# v3.0.0-beta.5

The largest release in the 3.0 series so far, and the first built with Xcode 27.
A command-line tool now ships inside the app bundle, inspecting "My Mac" no
longer risks the app itself, the sidebar ties a class's Swift and Objective-C
entries together, the source editor can be pointed at a specific Xcode, and the
app has a new icon. Several results that were quietly wrong are fixed too — a
Catalyst engine that never finished connecting, accessor addresses on
properties, Swift subclasses missing from Relationships, and RuntimeViewer's own
payload appearing among a target's images.

This is a `beta` build — only clients that opted in via
**Settings → Updates → Include pre-release versions** receive it. It runs on
macOS 15 or later, on both Apple silicon and Intel Macs, as before.

---

## A command-line tool ships inside the app

`runtime-viewer-cli` now lives at
`RuntimeViewer.app/Contents/Applications/runtime-viewer-cli`, signed and
notarised alongside the app. There is no installer step yet, so symlink it onto
your `PATH` yourself if you want a short name.

It covers the inspection surface rather than a corner of it: `images`, `load`,
`types`, `search`, `interface`, `hierarchy`, `relationships`, `members`,
`specialize` and `export`, plus `sources`, `attach` and `detach` for reaching
other processes. Every command accepts `--json`, so results can be consumed
without scraping text.

The app does not have to be open. The first command starts a background host
that stays warm between invocations and exits once it goes idle, so a second
query against an already-loaded image answers immediately. When the app *is*
running it becomes the host itself, and the CLI then sees exactly the images and
attached processes the window sees instead of loading a second copy of
everything.

## A crashing image no longer takes the app down

Images you open on "My Mac" used to be loaded into RuntimeViewer itself, so a
malformed Mach-O or an image whose initializers crashed took the whole app with
it. That work now happens in a small service embedded in the app. If it
crashes, you lose the images it had loaded, not the app: the windows return to
the image list, a notification says what happened, and the engine reconnects on
its own.

## A class's Swift and Objective-C entries point at each other

A Swift class that the Objective-C runtime also knows appears twice in the
sidebar, and until now only its Objective-C entry said so, with a blue `C`. Its
Swift entry now carries an orange `C`, and a class written with Swift's
`@objc @implementation` carries a pink `C` on both entries. Right-click either
entry for **Jump to Swift Class**, **Jump to Swift Implementation** or **Jump to
Objective-C Class** to reach the other one. Classes renamed with
`@objc(CustomName)` do not pair yet.

Every icon in the sidebar, Open Quickly and the Inspector's lists now has a
tooltip saying what it stands for.

## Reveal the current object in the sidebar

**Navigate → Reveal in Sidebar Navigator** (⇧⌘J, Xcode's shortcut for the same
thing) brings the object on screen back into the sidebar: it opens a collapsed
sidebar, clears a search or scope filter that hides the row, expands the row's
section and parents, and selects it.

## You can choose which Xcode the source editor comes from

The editor borrows its frameworks from an installed Xcode, and the search order
used to be fixed: an embedded copy, then whatever LaunchServices resolves
`com.apple.dt.Xcode` to, then `/Applications/Xcode.app`. With several Xcodes
installed there was no way to name one, and no way to route around a version
whose editor misbehaves.

**Settings → Editor** now offers Automatic, every Xcode LaunchServices knows
about with its version, and **Choose Another Xcode…** for a copy it does not —
which is where a version manager keeps them. The frameworks can only be loaded
once per process, so changing the selection asks you to relaunch and offers a
button to do it.

## A new app icon

The icon was rebuilt as separate layers instead of one flat image, so it now
adapts properly to the dark and tinted appearances and picks up the Liquid Glass
material. Pre-release builds carry a BETA badge, which makes a beta and a stable
install tellable apart in the Dock.

## Switching to the Mac Catalyst engine no longer loads forever

Selecting the Mac Catalyst engine could spin indefinitely with nothing reported.
The app treated the connection as established before the helper had connected
back, and a helper that resolved a different daemon — or a daemon reinstalled
during launch — failed silently, leaving an engine that nothing would ever
answer. The handshake is confirmed before the engine reports itself connected,
and the helper is relaunched when the daemon it talks to changes.

## Batch export reports what it is doing

Loading an image also builds its Objective-C and Swift indexes, and for a
framework the size of PhotosUICore that index is the longest step of the whole
export. Rows stayed on **Queued** for all of it. Each row is now marked running
before the load starts and shows the current indexing phase next to its bar.

## RuntimeViewer's own payload no longer shows up among a target's images

Inspecting another process means loading RuntimeViewer's code into it, so dyld
listed the payload bundle among the target's images — in the sidebar's Others
tree, in Open Quickly, and in the MCP image list — as if you had asked to inspect
RuntimeViewer's own scaffolding. It is filtered out now.

## Property accessors reported the wrong address

A property's accessor address came from a single table keyed by selector, built
from instance and class methods together. Objective-C lets both carry the same
selector — `-[NSObject description]` and `+[NSObject description]` both exist —
so the class method overwrote the instance one, and every instance property whose
getter shared a name with a class method reported the wrong address while still
printing `-[…]`. `NSObject` alone hits it four times.

## Other changes

- Private Swift types show their discriminator in the sidebar, `(Name in _…)`,
  so two private types with the same name from different files can be told apart.
- **Generation Options** has a new **Infers ObjC Overrides From Selector Names**
  switch, off by default. It prints `@objc override` on a Swift method whose only
  tie to an ancestor's Objective-C method is that its name matches the selector.
- Opening an image while background indexing runs waits less behind it: with five
  images set to always index, opening AppKit took about 10 s instead of 11.3 s
  (8.9 s with nothing indexing).
- Loading shows the system spinner, and the content pane is covered while an
  interface loads instead of showing the previous object's text underneath.
- On macOS 27 the sidebar and Inspector tab switchers use the system's tab style.

## Other fixes

- The Inspector's Relationships tab left out every Swift subclass of an
  Objective-C class. Present since 2.1.0.
- Selecting a Swift protocol nested in a type showed no conformers in Relationships.
- Far down a long object list, filtering or expanding a nested type could leave
  two rows drawn on top of each other.
- On macOS 27, pressing a row in a sidebar list and dragging moves the selection
  with the pointer again.
- After opening an image, clicking a row left its highlight grey on macOS 27, and
  right-clicking a row's text could open no menu at all.
- With scroll bars set to always show, the source editor no longer keeps an empty
  track beside an interface that fits.
- Errors raised inside three background tasks were dropped instead of surfaced.
- The sidebar and the Inspector's Relationships pane each kept a view model alive
  after the pane that owned it went away.
- On macOS 27 the sidebar's push and pop showed a flash of the window background
  between panes; both panes now hold a copy of the enclosing glass for the
  duration of the transition.
- The source editor's minimap shows its hover labels again, and the editor works
  under Xcode 27.
