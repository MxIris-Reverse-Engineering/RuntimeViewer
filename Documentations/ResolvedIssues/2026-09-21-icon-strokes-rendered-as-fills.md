# 2026-09-21 App 图标在 macOS 26 上糊成一块白疙瘩：Icon Composer 1.6 把描边图形当填充

**调查日期：** 2026-09-21
**修复落地：** 本日，见 `Resources/AppIcon.icon/Assets/DiscOutline.svg` 与 `Magnifier.svg`（两份描边图形改写成填充路径，`AppIconBeta.icon` 下同名文件同步）
**所属分支：** `next`
**Severity：** Major —— macOS 26 上 App 图标的主体图形完全不可辨识，且 macOS 26 是当前发布版本
**触发场景：** 用户把同一份 `AppIcon.icon` 分别用 Icon Composer 1.6（Xcode 26）和 Icon Composer 27（Xcode 27）打开并排对比，1.6 那边的黑色圆盘、白色外环和放大镜糊成一整块白色磨砂圆盘，27 那边正常

---

## 一览

| 字段 | 内容 |
|---|---|
| **现象** | dark 外观下，本该是「黑色圆盘 + 白色外环 + 白色放大镜 + 透出的代码」的前景，渲染成一整块不透明的白色磨砂玻璃圆盘，放大镜只剩一点隐约的轮廓 |
| **影响范围** | 只在 Icon Composer 1.6 / macOS 26 的渲染管线上出现。Icon Composer 27 / macOS 27 渲染同一份文档完全正常，legacy `.icns` 回退位图也正常 |
| **根因** | `DiscOutline.svg` 和 `Magnifier.svg` 是 `fill="none" stroke="#FCFCFC"` 的**描边**图形。Icon Composer 1.6 的 SVG 管线不支持 `stroke`：它忽略描边、把图形当**填充**处理，于是那个本该是细圆环的 `<circle>` 变成一块实心圆盘，盖住了它下面的 `Disc.svg` |
| **Status** | **Fixed** —— 两个图形改写成填充路径（圆环 = 双圆 `fill-rule="evenodd"`，手柄 = 圆角胶囊），macOS 26 渲染器下圆盘中心从 rgb(225, 234, 242) 回到 rgb(15, 15, 15)。填充路径在两个渲染器上都正确，不需要按版本分叉 |

---

## 怎么定位的

图标最终外观由**运行的系统**合成，不是 actool 定死的，所以先搭了一条能变红的回路：actool 编译 `.icon` → 把 `Assets.car` 塞进一个临时 app bundle → `lsregister -f` → `NSWorkspace.icon(forFile:)` 取系统合成结果 → 写成 PNG。一次迭代约十秒，圆盘中心像素值就是判据。基线复现了用户截图左半边。

排除过程（全部是对照实验，不是推理）：

| 实验 | 改动 | 圆盘中心 | 结论 |
|---|---|---|---|
| 基线 | — | (225, 234, 242) | 复现 |
| `Disc` 层 `glass: false` | 关玻璃 | (225, 234, 242) | 无关 |
| 三层全部 `glass: false` | 关玻璃 | (228, 238, 245) | 无关 |
| group `translucency.enabled: false` | 关半透 | (229, 239, 247) | 无关 |
| `Disc` 单独成组 / 移入代码层那一组 | 改分组 | (223, 233, 240) | 无关 |
| **`Disc` 的 dark 填充改成纯红** | 换颜色 | (225, 234, 242) | **颜色根本没参与** |
| `Code Listing` 的 dark 填充改成纯红 | 换颜色 | (73, 42, 42) | 特化机制本身是好的 |
| **只保留 `Disc` 一层** | 隐藏另两层 | **(15, 15, 15)** | 黑盘本身没问题 |
| **只保留 `Disc Outline` 一层** | 隐藏另两层 | (223, 233, 240) | **一个圆环把整个圆填满了** |
| 只保留 `Magnifier` 一层 | 隐藏另两层 | (225, 235, 242) | 同上 |
| **两个描边图形改成填充路径** | 换几何 | **(15, 15, 15)** | 命中 |

倒数第二、第三行是转折点：一个 `fill="none"` 的圆环单独渲染时，圆心是白的。那一刻嫌疑就从「玻璃材质吃掉了颜色」转到了「这个圆环根本不是圆环」。

一个反过来的旁证：把 `Disc` 的 dark 填充改成纯红，渲染一个像素都不动；而 `Code Listing`（本来就是填充路径）改成纯红立刻变暗红。同一个 `fill-specializations` 机制，一个生效一个不生效，差别只在图形是描边还是填充。

## 几何怎么换算

原始描边的测量值记在两个 SVG 的注释里，填充路径严格沿用：

- **外环**：描边中心线 r=216.75、宽 16.5 → 外圆 r=225、内圆 r=208.5，单条 path 双圆 `fill-rule="evenodd"`
- **镜片**：描边中心线 r=83.8、宽 16 → 外圆 r=91.8、内圆 r=75.8，同样写法
- **手柄**：`(445,445)` 到 `(521,523)`、宽 16、`stroke-linecap="round"` → 半宽 8 的胶囊。**圆帽要算进去**：round cap 让线条在两端各**外延 8**，胶囊的两段半圆弧圆心就落在原来的两个端点上，否则手柄会短一截

换完之后拿 legacy `.icns`（actool 的静态回退渲染，走的是另一条管线）交叉验证：改动前后逐像素比对只在圆盘区域有 7200 像素的抗锯齿级差异，环粗、镜片大小、手柄角度一致。

## 留下的约束

**这个图标的 SVG 资产一律不许用 `stroke`。** 两个文件的头注释都写明了原因。`CodeListing.svg` 由脚本生成、本来就是轮廓填充，`Grid 10pt.svg` 出自 CoreSVG 导出、也是填充，只有这两个手写的几何是描边——它们从 2026-09-20 重建图层那次起就是错的，只是当时只在 Icon Composer 27 里看过效果。

顺带记一条相邻事实（与本 bug 无关，但同一次调查查实）：**Xcode 26 的 actool 打不开 Icon Composer 27 的文档**，顶层 `"features"` 键会让它报 `Could not open "…"` 并且一个文件都不产出。处理方式见提案 [0020](../Evolutions/0020-icon-composer-document-variants.md)。
