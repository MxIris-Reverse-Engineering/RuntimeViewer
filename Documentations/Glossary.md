# RuntimeViewer 术语表

收录本项目自造的名字、内部代号、带项目特定含义的通用词，以及容易混淆的近义词对。通用的
Swift / Apple 框架词汇不收。跨项目通用的术语见全局术语表。

| 术语 | 含义 | 出处 |
|---|---|---|
| **CLI host** | 承载 `runtime-viewer-cli` 的常驻进程：持有运行时引擎与索引，客户端每条命令都是短命的薄进程。App 不在跑时由第一条命令在后台拉起，空闲到期自动退出；App 在跑时由 App 充当（见 host takeover）。用户口中的「Helper」，愿景改称此名以区别于特权 helper daemon 与 Catalyst helper | [愿景《无头 RuntimeViewer》](Visions/HeadlessRuntimeViewer.md)、[0034-command-line-interface-foundation](Evolutions/0034-command-line-interface-foundation.md) |
| **source selector** | `--source` 的取值，指明命令跑在哪个运行时来源上：`local`、`catalyst`、`pid:<n>`、`process:<名>`、`engine:<id>`。全集在基础提案里一次定死，多来源提案起全部可用；`sources` 命令为每个来源给出可回填的 selector | [0034-command-line-interface-foundation](Evolutions/0034-command-line-interface-foundation.md)、[0036-command-line-interface-multi-source](Evolutions/0036-command-line-interface-multi-source.md) |
| **host takeover（App 优先）** | RuntimeViewer App 启动时接管 CLI host 的角色：先请正在跑的独立 host 排空退出（`shutdownHost(.applicationTakeover)`，超时则 `SIGTERM`），再自己绑定同一个 socket（`host.json` 的 `kind` 为 `application`）。同一时刻只有一个进程做 Bonjour 客户端与注入者；App 退出后下一条命令再拉起独立 host。代码在 `HostTakeover` 与 App 的 `CommandLineHostController` | [0036-command-line-interface-multi-source](Evolutions/0036-command-line-interface-multi-source.md) |
| **helper daemon** | 经 `SMAppService` 安装的特权 daemon（`com.JH.RuntimeViewerService`），负责注入与列进程；与 CLI host 无关 | `AGENTS.md`「Helper Service」 |
| **Catalyst helper** | 嵌在 App 包 `Contents/Applications/` 里的 Mac Catalyst 应用，经 helper daemon 拉起、再经它连回来，为 **CLI 独立 host** 提供 Catalyst 运行时引擎；App 自己用 Catalyst service。与 CLI host 无关 | `AGENTS.md`「Embedded non-macOS products」、[0051-catalyst-xpc-service](Evolutions/0051-catalyst-xpc-service.md) |
| **Catalyst service** | 嵌在 App 包 `Contents/XPCServices/` 里的 Mac Catalyst XPC service `RuntimeViewerCatalystService.xpc`，App 的「My Mac (Mac Catalyst)」引擎在这里执行。不经 helper daemon，launchd 在 App 自己的 bundle 里按需拉起，崩了由连接自动重连。它和 Catalyst helper 都只是外壳：真正干活的是两者从 App 的 `Contents/PlugIns` 加载的同一个 `RuntimeViewerCatalystHelperPlugin` | [0051-catalyst-xpc-service](Evolutions/0051-catalyst-xpc-service.md) |
| **本地运行时 service（local-runtime service）** | 随 App 打包在 `Contents/XPCServices/` 里的普通 XPC service `RuntimeViewerLocalRuntimeService.xpc`，「My Mac」引擎真正 `dlopen` 与索引镜像的进程。不经 Mach service，不经 helper daemon，launchd 在 App 自己的 bundle 里按需拉起；崩了只丢已加载的镜像，App 不受影响 | [0037-local-runtime-xpc-service](Evolutions/0037-local-runtime-xpc-service.md) |
| **Find 语料（interface corpus）** | 引擎为 Find 的文本与成员搜索保存的 interface 文本，每个镜像一份、住在拥有该镜像的进程里（`RuntimeInterfaceCorpusStore`）。每个对象只打印一次：MachOObjCSection / MachOSwiftSection 的标记模式把受 Generation Options 控制的内容全部打出来，并用 swift-semantic-string 的可见性区域标上在什么选项下可见；搜索时按内容区当前的选项**投影**（删掉不该显示的区域）再匹配，所以搜到的行与内容区逐字节相同。只有 transformer 变化才重建 | [0029-find-navigator](Evolutions/0029-find-navigator.md) |
| **补搜（widening search）** | Find 面板上已有结果时，搜索开始后才建好的语料由会话再搜一次、把命中并进屏上的结果（`FindSession` 的 widening search）。它是一次独立的引擎搜索，只读新建好的那几个镜像：总数与折叠计数累加，范围沿用当初那次搜索解析出的镜像集合；失败时保留已有结果、只记日志。与「重新搜索」不同，屏上的结果不清空 | [0029-find-navigator](Evolutions/0029-find-navigator.md) |
| **协议副本（protocol copy）** | 同一个 `@protocol` 声明在每个见过它的镜像里各有一份 `protocol_t`，侧栏按 `__objc_protolist` 全量列出（`ResolvedIssues/2026-08-05-objc-protocol-ownership-filter.md`）。一次文本或成员搜索内部，与已报告命中的同名副本在当前选项下逐字相同的副本只计数，进摘要的 `omittedRepeatedMatchCount`，Find 摘要栏写「N more in identical protocol copies」；文本不同的副本照常各报一次。类型关系树按「范围内路径最小」选代表副本 | [0029-find-navigator](Evolutions/0029-find-navigator.md) |
| **rendezvous（报到信息）** | 注入方交给载荷的一切：宿主的可达地址、端口，以及这次注入的认领令牌。以 `rendezvous.json` 写在暂存目录里载荷旁边，载荷启动时读。存在的理由是消除「载荷在别人的进程里推导自己是谁、该连到哪」这一整类问题 —— 两者在目标进程里都答不可靠。为 nil 表示「自己广播」，那是模拟器走的路 | [`DevicePayloadReverseConnection.md`](DevicePayloadReverseConnection.md)、[0044-device-payload-reverse-connection](Evolutions/0044-device-payload-reverse-connection.md) |
| **认领令牌（claim token）** | rendezvous 里的一次性标识，载荷连上时原样呈上，宿主只认自己发出去的那一个。**它只做区分，不做认证** —— 和载荷同在一个世界可读的目录里，谁能读到它也就能加载旁边那个载荷。一次注入一个，所以两次并发注入不会把先到的交给错误的请求 | 同上 |
| **反向连接（reverse connection）** | 真机上载荷不监听、改为主动连回宿主的那条路径。叫「反向」是相对 Bonjour 而言：那条是设备广播、宿主连进去 | 同上 |
| **挂起（suspended）** | iOS 进程被停到没有任何线程被调度的状态，App 离开前台后一秒内就会进入。**不是「慢」，是「完全不执行」** —— 注进去的代码不会跑，等它回报的一方等多久都等不到。系统里的判据就是 `RBProcessState.preventSuspend` 这一个布尔值 | [`DevicePayloadReverseConnection.md`](DevicePayloadReverseConnection.md) 第八节、[0045-device-process-assertions](Evolutions/0045-device-process-assertions.md) |
| **assertion（RunningBoard assertion）** | 向 iOS 的进程生命周期管家 `runningboardd` 声明「这个进程要保持某种状态」的一张凭据。本项目只用一种：带 `RBSLegacyAttribute`（`reason 10004` = `FinishTaskUnbounded` / `flags 1`）的那种，效果是目标不被挂起。**凭据的寿命就是承诺的寿命** —— 持有它的对象一消失，RunningBoard 就收回。目标可以是别的进程，这正是「注入 App 不需要先保活自己」的原因 | 同上 |
| **受限 entitlement（restricted entitlement）** | iOS 上一类 entitlement：消费它的守护进程另带一份按 bundle id 的白名单，不在名单里的进程在**读取阶段**就被剥掉这一条，签名里有也没用。`com.apple.runningboard.primitiveattribute` 就是其中之一，名单在 `/System/Library/RunningBoard/runningboardEntitlementsConfiguration.plist`。判断一条私有 entitlement 可不可用，必须跟到消费方构造权限集合那一步，只看检查点会得出相反结论 | 同上 |
| **保活（keeping awake）** | 本项目里专指「持有 assertion 让某个进程不被挂起」，有两处用法：越狱版对自己（所以切出前台仍能应答），以及对注入目标（所以注得进去、也连得住）。**不是**后台任务、静音音频那类「假保活」 | 同上 |
| **镜像引擎（mirrored engine）** | 经 Bonjour 对端转发过来的第三方引擎，在对端的引擎列表里出现、由本机的 proxy 层代理 | [`EngineMirroringWalkthrough.md`](EngineMirroringWalkthrough.md) |
| **合成扩展（synthetic extension）** | MachOSwiftSection 索引器为「父级不是本镜像里的类型」的嵌套类型生成的 `ExtensionDefinition`：父级是扩展上下文、是别的镜像的类型、或只能经符号找到时，把类型包进 `.types`，按被扩展类型的键存进 `typeExtensionDefinitions`。源码里并没有这样一个扩展块，它只是给无处安放的嵌套类型找个落脚处 | [`SwiftObjectTreeWalkthrough.md`](SwiftObjectTreeWalkthrough.md) |
| **并入（folded extension）** | `RuntimeSwiftSection.allObjects()` 对「键对应的类型 / 协议就在本镜像里」的扩展与协议遵循的处理：不在侧栏单独列一条，内容拼进那个类型 / 协议节点的 interface，扩展里声明的类型挂成它的子节点。与「单独列出的扩展节点」相对 | [`SwiftObjectTreeWalkthrough.md`](SwiftObjectTreeWalkthrough.md) |
| **命令扩展（command extension）** | 一组由 `RuntimeViewerCore` 之外的模块声明、在运行时装进引擎命令表的 RPC 命令。那个模块自己 `extension RuntimeEngine.CommandName` 声明短名（命名空间前缀不变 —— 它是线上契约），把遵循 `RuntimeEngineCommand` 的命令类型归在自己的命名空间下，再用 `RuntimeEngine.addCommandExtension(named:install:)` 登记；Core 一行不改。代价是**每个 serve 引擎的进程都要在入口显式调一次那个模块的 install**，漏调没有编译错误。`RuntimeViewerInjection` 是第一个，也是范式 | [0047-open-command-registry-and-injection-module](Evolutions/0047-open-command-registry-and-injection-module.md) |
| **内置命令（built-in command）** | 与命令扩展相对：`RuntimeViewerCore` 自己的那三十来条命令，清单在 `RuntimeEngine.registerBuiltInHandlers(into:)`，每条连接上**先**装它们。因此先到先得的重名拒绝意味着外部模块抢不走 Core 的命令名 | 同上 |
| **私有鉴别器（private discriminator）** | Swift 给 `private` / `fileprivate` 声明加的标识，让不同源文件里的同名声明互不冲突。demangler 打开 `showPrivateDiscriminators` 时把它写成 `(Name in _HEX)`：`_` 后面 32 位大写十六进制，就是 `MD5(模块名 + 源文件名)`。在 demangle 出的树里它是 `privateDeclName` 节点的第一个子节点，第二个是声明名。引擎打印 `displayName` 时不打印它，而是把名字读得到的私有声明放进 `RuntimeObject.privateDeclarations`（读法是 MachOSwiftSection 的 `DemanglingNode.privateDeclarations`）；侧栏据此在行尾放一个 `Private` tag。点 tag 弹出的 popover 给出原值，以及引擎用镜像里的名字和开源项目里的真实文件名去猜、MD5 对上才算数的源文件名（引擎命令 `privateDeclarationSourceFiles`，搜索本身在 MachOSwiftSection）。旧文档里也写作「私有判别符」 | [0031-private-discriminator-tag](Evolutions/0031-private-discriminator-tag.md) |
| **局部类型（local type）** | 声明在函数或闭包体里的 Swift 类型。侧栏把它挂在声明那个函数的类型下面，名字照 MachOSwiftSection 给读者的写法：不带模块名和参数类型，保留 `#1` 序号，如 `Visitor #1 in TableDataSource.performDrop(to:)`；行尾带一个不可点的 `Local` tag（`RuntimeObject.Properties.isLocalType`）。嵌在局部类型里的类型名字同样这么写，但不算局部类型、不带 tag。二进制里找不到所在函数时，名字带包着它的匿名上下文的地址，如 `TableDataSource.(Visitor in $1a2b3c)`，称为按位置命名（`isPositionNamedLocalType`）；那个 `$` 开头的数不是私有鉴别器 | [0031-private-discriminator-tag](Evolutions/0031-private-discriminator-tag.md) |
| **书签作用域（bookmark scope）** | 书签与侧栏展开状态落盘时用的键（`RuntimeBookmarkScope`），由运行时来源派生，但不等于来源：`RuntimeSource` 回答「往哪里连、以什么角色连」，它的 Bonjour 标识带 pid、对端一重启就变，显示名又会在两台设备的同名进程之间撞车，都不能当持久化键。每种来源取自己已有的稳定标识，写成可读、可反向解析、带版本号的字符串，如 `v1:bonjour:client:{deviceID}:SpringBoard`；取不到稳定身份时退到 legacy | [0033-runtime-bookmark-scope](Evolutions/0033-runtime-bookmark-scope.md)、[`CommunicationAndEngineArchitecture.md`](CommunicationAndEngineArchitecture.md) §2.3 的注 |
| **Engine 键（engine key）** | Always Index 的条目用来认 Engine 的键（`Settings.Indexing.EngineReference.key(for:)`），写在 `settings.json` 里。默认是 `scope:` 加该 Engine 书签作用域的键；**本机 Attach 的进程是例外**：它的书签作用域带 pid、目标一重启就变，所以改用 `process:` 加进程名，同名进程共用一个选择。书签恰恰不许这样认（同名进程不能共用书签），用户写的匹配规则要的正是这样 | [0054-always-index-per-engine](Evolutions/0054-always-index-per-engine.md) |
| **Engine 的后台工作（engine background work）** | 一个 Engine 的后台索引、Find 语料与交叉引用预建三件事（`RuntimeEngineBackgroundWork`），由这个 Engine 上的所有文档共用：一个 Engine 只有一个后台索引协调器、一个语料协调器、一个交叉引用预建协调器，所以同一 Engine 的窗口显示同一份 Report，Cancel、Cancel All、Clear History 在哪个窗口点都对所有窗口生效，只有 Engine 不同的窗口 Report 才不同。文档只经显式的 `DocumentState.startBackgroundWork()` 加入（`Document.makeWindowControllers` 的第一句），读协调器不会加入；第一个文档启动时建立，**最后一个文档离开**（关窗或切到别的 Engine）**时关闭**：取消还在跑的批次、语料构建与预建，Report 清空。它也替这个 Engine 上的所有文档算出「有没有活在跑」（Report 页签的活动标记），并持有防 App Nap 的 activity，有活时持有、关闭时放掉 | [后台工作按 Engine 共享](Evolutions/0055-engine-scoped-background-work.md)、[ResolvedIssues/2026-10-16](ResolvedIssues/2026-10-16-second-document-disturbs-shared-indexing.md) |
| **RuntimeEngineSession** | 文档所在的 Engine，加上文档在它上面的后台工作，合成的一个对象（`DocumentState.runtimeEngineSession`），二者放进去就不再改变。消费者只跟随这一个值，Engine 和它的工作总是一起换，不会读到一个新、一个旧。文档启动后台工作、切到别的 Engine 时换一个新 session；同一个 Engine 背后的进程重启、有内容打开时，**保留原 session**，只再赋值一次，让接口缓存等跟着重来；关闭时只调 `leave()`，不换 session。没启动的文档，session 不持有工作（`backgroundWork` 为 `nil`）。不要和 `RuntimeBackgroundIndexingCoordinator` 里按「这一次连接」计数的 `connectionGeneration` 混为一谈 | [DocumentState 瘦身](Evolutions/0058-runtime-engine-session.md) |
| **Tuist 开发 workspace / 原生工程** | 构建 macOS App 的两条路。**原生工程**指仓库里手工维护的三个 `.xcodeproj` 与三个 workspace，是发版、CI 和所有脚本的唯一依据。**Tuist 开发 workspace** 指 `./TuistScript.sh` 用 Tuist 生成的 `RuntimeViewer-Tuist.xcworkspace`，只供日常开发：同样的 target、源码与 `Configurations/` 下的 xcconfig，第三方依赖取自本机的 Tuist 二进制缓存，四个本地包保持源码。生成物都在 `.gitignore` 里；两边的一致靠「同批同步」规则和 `./TuistScript.sh check` | [`Guides/TuistDevelopment.md`](Guides/TuistDevelopment.md)、[0053](Evolutions/0053-tuist-coexistence.md) |
| **派生数据（derived data）** | 服务进程从共享缓存里的系统镜像和自己的代码算出来、存在盘上的东西，借 Xcode DerivedData 的名字：系统没更新、代码没换，下次启动就读回来而不重算。目前只有 Find 语料一种（`RuntimeDerivedDataKind.interfaceCorpus`）。放在 `~/Library/Caches/<App 的 bundle id>/DerivedData`，按**系统身份**与**生产者身份**分目录；只有两个服务进程（本地运行时 service、Catalyst service）在入口处显式开启后才读写与清理，App 进程只统计大小和整体删除。只管共享缓存里的镜像 | [派生数据](Evolutions/0061-derived-data.md)、[`DerivedData.md`](DerivedData.md) |
| **系统身份（system identity）** | 派生数据第一层目录的名字（`RuntimeDerivedDataSystemIdentity`）：平台（macOS / Mac Catalyst）、系统版本、build（`kern.osversion`）与 dyld 共享缓存 UUID。系统一更新，build 和共享缓存都变，旧目录在服务进程第一次用到派生数据时被清掉 | 同上 |
| **生产者身份（producer identity）** | 派生数据第二层目录的名字（`RuntimeDerivedDataProducerIdentity`）：含 RuntimeViewerCore 的那个映像与它在本进程里加载的非共享缓存依赖，各取内存里的 `LC_UUID` 与名字（install name 或文件名，不带路径）算出的摘要。代码一变就是另一个生产者，所以绝不会读到旧代码的产物；同一 bundle id 的多份构建（几个 worktree）各用各的目录、互不删除，14 天没用过的才被清掉 | 同上 |
| **读取标记（reading marker）** | 读一个派生数据文件之前放在它旁边的 `<文件名>.reading`，记着读者的 PID 与启动时间，等读回的语料完整遍历过、两次投影都做完才删。下次读时发现标记、而那个进程已经不在，说明上次读到一半崩了，文件不读、直接删掉，坏文件因此最多让服务崩溃一次。标记里的进程还活着，就当作别的实例正在读，这次不读也不删 | 同上 |
