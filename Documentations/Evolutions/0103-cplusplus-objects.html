摘要

RuntimeViewer 新增第三种对象语言：C++。镜像的对象列表在 Objective-C、Swift 之外列出 C++ 的类与命名空间，嵌套的作为子项。类有两个来源，按限定名合并：MachOKitExtensions 3.1.0 的 CPlusPlusClassIndexStore 读 RTTI（Itanium C++ ABI 的运行时类型信息）与 vtable（虚函数表），符号被剥离的类也找得到；3.0.0 起的 CPlusPlusSymbolIndexStore 按作用域归类镜像的 C++ 符号，给出看得出是类型的作用域与命名空间。

内容区把一个类打印成伪头文件：基类、按槽位排列的虚函数（自己没名字的沿基类补名，并标出是覆盖还是继承）、非虚成员函数与变量，槽位号与地址写在注释里；命名空间打印其中的自由函数与变量。点基类名跳到基类（基类在别的镜像也行），Inspector 显示主基类链与本镜像里的派生类，Filter Scope 多一组 C++，图标是绿色的 C 与 N。

C++ 对象只发给声明要它的请求方：objectsInImage 命令加一个可选字段，旧版对端跳过它、照旧只回 ObjC 与 Swift。本版里也只有侧栏、路径栏与镜像页去要，Find、导出、MCP、CLI 都看不到 C++ 对象，它们以后各自另写提案。

要你定

没有待定的事

实现中发现的两处上游问题都已按用户批准在 MachOKitExtensions 修复：N_INDR 条目被当成定义的符号（3.2.1）；ObjC 方法被判成「未定」作用域，且签名里的类型没有位置（3.3.0，上游提案 0008）。本提案的下限随之抬到 3.3.0。

与澄清提问里的样例不同的地方

  • Itanium 修饰名只给函数模板特化记返回类型，所以大多数函数打印不出返回类型。
  • 修饰名不区分静态成员，也不记访问级别，所以不写 static、不写 public:。

提议方案

  1. 新种类 RuntimeObjectKind.cPlusPlus(.class | .namespace)，排在 C 之后、Objective-C 之前（侧栏分节、路径栏、镜像页计数、Filter Scope 都按这个顺序）；新语言 RuntimeInterfaceLanguage.cPlusPlus（"cpp"）。修饰名分不出 struct 与 class，一律叫类。
  2. 每个镜像一个按需建的 C++ section，第三个工厂照 ObjC 工厂的形状缓存与合并构建；不属于「已索引」，后台索引、语料都不碰它。
  3. 对象树：类型作用域与 RTTI 类是类（按限定名合并，RTTI 优先）；命名空间与「未定」作用域是命名空间；函数作用域丢弃；只有 RTTI 的类按 scopePath 挂进去、缺的层补齐；没有会打印的成员、也没有子对象的命名空间不列；全局有成员时列一个 ::（Global Namespace）；同名隐藏类留 typeinfo 偏移最小的。
  4. 只发给要它的请求方：ObjectsInImageCommand 加 includesCPlusPlusObjects: Bool?（nil 不编码），公开 API 默认 false；只有侧栏、路径栏、镜像页传 true。
  5. 进度：两个新阶段，只在请求带字段时发出。
  6. 伪头文件：类的头部注释、基类、每张 vtable 的虚函数（槽位号、地址、overrides / inherited）、非虚成员函数、变量、嵌套类型；构造与析构变体合并；元数据符号不当成员；只打印修饰名里有的；地址跟随 addMethodIMPAddressComments；参数与返回类型里的命名类型按上游给的位置打印成类名记号（模板连同实参一个）。
  7. 跳转：C++ 记号按文字链接；本镜像找不到就要到基类修饰名，按导出的 _ZTI… 找定义它的镜像；非唯一 RTTI 找不到就不跳。参数与返回类型里的类名同样建链接。
  8. 补名的搜索路径：独立文件用目录的 dependencySearchPaths(forImageAt:)。
  9. Inspector：主基类链与本镜像里的派生类（「Derived Classes」）。
  10. App：Filter Scope 在 C 与 Objective-C 之间的 C++ 组、绿色 C / N 图标、"cpp" 语言标识（桥接对应到重建版的 SourceModelEditorLanguage.cpp，框架解析给关键字着色、语义区间重新标注类型与成员）、cPlusPlusHeader 与 hpp、镜像页计数。
  11. 依赖：MachOKitExtensions 下限 3.3.0，Core 加 CPlusPlusSymbols，锁文件只移这一个包；Tuist.swift 补上 3.2.0 新增的两个 target。
非目标
  • Find（语料、成员搜索）、导出、MCP、CLI、命名词云、派生数据都不接 C++。
  • 交叉引用：C++ 对象没有成员地址，不提供 Callers / Callees / Type References；交叉引用里的 C++ 名字仍不 demangle。
  • 字段（RTTI 与 vtable 不带字段，protobuf 是上游之后的提案）。
  • 修饰名没记的返回类型、static、访问级别的推断。
  • 函数作用域里的局部实体。
  • 别的镜像里的派生类；借用 shared cache 镜像时跨 owner 合并 C++ 层级。
  • C++ 界面的注释标签（不标注释结构）。
  • 新的 RuntimeObject.Properties 位（例如「只从 RTTI 恢复」）。
  • MachOKitExtensions 之外的 C++ 来源（ObjC ivar 编码里的 C++ 结构体）。

level：类 2、命名空间 3，紧接 C 的两种；ObjC 顺延为 4–7、Swift 为 8–22。level 私有、只供排序，不上线也不落盘。命令把 false 编成 nil，只有 true 上线；借用 shared cache 镜像的 engine 把整条命令交给主人，字段随之过去。

工厂、section 与协议

    nonisolated var imagePath: String { get }

    func mangledTypeName(ofBaseNamed qualifiedName: String) -> String?
    func interface(for object: RuntimeObject, options: RuntimeObjectInterface.GenerationOptions) async throws -> RuntimeObjectInterface
    func primaryBaseChain(of object: RuntimeObject) async throws -> [(qualifiedName: String, object: RuntimeObject?)]
    func derivedClasses(of object: RuntimeObject) -> [RuntimeObject]

  • section 建成时依次 prepare 作用域树、取 classes(in:)，各报一个阶段（上游不报进度，只报 0/1 与 1/1），再交给建树。
  • section 只存对象树与两张字典；成员与 vtable 打印时向上游 store 取。
  • removeAllSections() 让两个上游 store 丢掉这些镜像；上游补名顺带给基类镜像建的索引 RuntimeViewer 清不到，写进实现说明的已知局限。
打印示例与规则 
// libc++abi · typeinfo 0x1A2B30 · vtable 0x1C4F00
class std::bad_array_new_length : public std::bad_alloc {
    // Virtual functions (primary vtable)
    virtual ~bad_array_new_length();       // slots 0–1  0x0004A3C0, 0x0004A3E0
    virtual what() const;                  // slot 2  0x0004A510  overrides std::bad_alloc

    // Member functions
    bad_array_new_length();                // 0x0004A100, 0x0004A120
};
  • 槽位注释的结尾：overrides、inherited from，或什么都不写（类自己引入，或基类读不到）。没名字的槽位写 virtual /* unnamed */;，纯虚 = 0，deleted = delete。
  • 实现在别的镜像时写 in <install name> 或地址；副表标出子对象与 offset-to-top。
  • 非 public 的基类写成 /* not public */ 基类。
  • hasTypeInfoSymbol == false 注明「只从运行时类型信息恢复」；hasUniqueTypeInfo == false 注明 typeinfo 按名字比较。
  • 命名空间：自由函数、变量、子项的前置声明；全局对象打印成 // Global namespace 加成员。
  • 记号里的类名与命名空间名写完整限定名；跳转种类：type(.class, _) → 类，type(.other, _) → 命名空间。
Inspector
  • .cPlusPlus(.class)：层级页（父类链）与关系页；.cPlusPlus(.namespace)：都没有。
  • 关系页标题「Derived Classes」，内容是 relationships.subclasses。
  • superclassChain 的节点 TypeKind 用已有的 class，线上形状不变。

已知问题（上游，已在 3.2.1、3.3.0 修复）

MachOKitExtensions 3.2.0 及以前的符号扫描没有排除 N_INDR 条目，libc++ 逐个转出的 std::exception 符号被当成 libc++ 自己的。3.2.1 起两条符号表路径都跳过它们，3.3.0 起，外层不带参数的局部名（ObjC++ 里 ObjC 方法的局部静态变量）也是函数作用域，QuartzCore 不再列出 -[CAMetalDrawable texture] 这类命名空间。本提案的下限抬到 3.3.0。

现状代码
  • 种类三支、合成 Codable；对象过 XPC 与 TCP、进语料快照、进书签，旧版本解不开新种类。
  • Filter Scope 记忆存排除的种类、逐条宽松解码；书签经 @ResilientFileStorage 逐条容错。
  • 对象列表由 _objects / _localObjectsWithProgress 拼 ObjC 与 Swift 两个工厂的结果；工厂只在 RuntimeImageIndex 建；手工同调两个工厂的还有停止、加载、后台索引、语料。
  • App 里取对象的：侧栏、路径栏、镜像页、命名词云、导出、后台索引、MCP（七处）、CLI。
  • 读取器：进程内 MachOImage，文件模式 MachOFile，两者都遵循 MachORepresentableWithCache；目录已有 image(definingObjCType:) 与 dependencySearchPaths(forImageAt:)。
  • 界面按种类分派，颜色只看 SemanticType；ObjC/C 的跳转按记号文字；SourceEditor 桥接只认 swift、objc，别的标识没有语言服务，整页不着色（写提案时误记为「只按语义区间上色」）；重建版自带 SourceModelEditorLanguage.cpp 与 C++.xclangspec。
  • 线上规矩（§4.4）：改已有命令加可选字段；新命令会让经 Mach service 的旧版注入 payload 断线（PR121.73）。
上游能力（MachOKitExtensions 3.1.0）
  • 作用域树：childScopes、scope(named:)、members(of:)、symbols(for:)；作用域种类 namespace / type / function / undetermined。
  • 名字：返回类型只有函数模板特化才有；不区分静态成员，不记访问级别。
  • 类索引：classes、class(named:)、derivedClasses、virtualTables（独立文件可给依赖搜索路径）；类带基类、typeinfo 与 vtable 信息，槽位带实现、名字与基类函数。
  • 耗时（debug）：Espresso 进程内建索引 0.29 秒、补名 2.2 秒，cache 文件 8.0 秒与 9.7 秒；TSTables 2.2 秒与 1.1 秒；JavaScriptCore 作用域树 release 约 0.15 秒。
  • 已知局限：有虚基类且无 __ZTV 符号时可能取错表组；基类的基类里的虚基类不展开；JavaScriptCore 关了 RTTI。
  • 平台与 Core 一致；Tuist 已列 CPlusPlusDemangling、CPlusPlusSymbols。

替代方案

9 条，均已否决
  • 新命令分两次取：旧版注入 payload 会断线（PR121.73）。
  • 无条件并进回复：旧版 App 整张列表解不开；Find、导出、MCP、CLI 也会收到处理不了的对象。
  • 随索引一起建：Always Index 的每个镜像都要多建一次，而只有侧栏用得到。
  • 按 vtable 逐格的报告式界面：用户选了伪头文件。
  • 只列 RTTI 类 / 只列类型：用户选了类型与命名空间都列。
  • 一次接上 Find、导出、MCP、CLI：用户选了只接浏览用的界面。
  • 为 C++ 另加地址开关：要改生成选项的线上形状与设置页，共用 ObjC 的开关足够。
  • 猜返回类型、static、访问级别：猜错比不写更误导。
  • 放进单独的命令扩展模块：本提案不加命令，C++ 与 ObjC、Swift 并列，放进 Core 的 Sections/。

影响

用户可见变化

  • 侧栏、Open Quickly、路径栏多出 C++ 的类与命名空间；镜像页计数多两行。
  • 内容区显示伪头文件、可跳转；Inspector 有层级页与「Derived Classes」页；Filter Scope 多一组 C++。
  • 没有移除任何已有界面；ObjC 与 Swift 完全不变；C++ 暂不出现在 Find、导出、MCP、CLI 里。

可发现性

默认开启，打开带 C++ 的镜像就列出；嫌多可用 Filter Scope 关掉，按 Engine 与镜像记住。

数据与配置兼容

  • 书签：降级到旧版时只丢 C++ 的那几条（逐条容错），不做迁移。
  • Filter Scope 记忆：旧记忆里没有 C++，C++ 默认显示；旧版读新记忆只丢那一条。
  • 派生数据格式不变；线上两种新旧组合由冻结测试守住。

平台与最低版本

最低版本不变；iOS、visionOS、越狱版共用侧栏的 ViewModel，也列出 C++ 对象；注入 payload 多带一份 ItaniumDemangle，第 1 步记下体积增量。

发布

无新权限、entitlement 或隐私清单条目，不影响公证与 Sparkle；发版前照常编 Distribution workspace。
