Draft - AppCore 不再使用 AppKit/UIKit 模型

状态 Accepted 作者 JH 创建 2026-11-18 对应提案最后更新：2026-11-18

原文：draft-app-core-without-ui-models.md（以原文为准）。关联提案：0091（拆 AppCore 与 AppUI，本提案推翻其中「UI 框架的模型可以留在 AppCore」一条）、0005（cell ViewModel 的 Appearance 单流）、0090（镜像种类图标）。

摘要

RuntimeViewerAppCore 的代码里不再出现 AppKit/UIKit 类型。图标和图标颜色改成描述值 IconDescriptor、ColorDescriptor；行标题改成带语义角色的 RowText；内容页的 ViewModel 输出 ContentInterface，即生成器给的语义串 FrozenSemanticString 加上链接与声明成员两张旁表。主题（ThemeProfile、ResolvedTheme、上色代码）整体搬进 RuntimeViewerAppUI，由 AppUI 的渲染环节 ContentTextRenderer 在后台把语义串变成富文本，只有显示富文本的 NSTextView 内容视图和 iOS 内容视图用它；正式构建用的 SourceEditor 视图本来就不显示上过色的富文本，从此每次显示少建一份。剪贴板和 Finder 改走跨层依赖，修饰键的换算搬进 AppUI。做完以后 AppCore 的 ViewModel 状态全是值类型，可以直接拿来序列化（为以后 Reflex 式的 ls / do 内省铺路，那是另一份提案）。边界测试加两条规则守住：不 import AppKit/UIKit，代码里不出现 AppKit/UIKit 的类型名。分四步合进 next，用户看到的行为不变。

要你定的事

方向已在两轮澄清提问中定下；剩下的是批准这份提案（状态改为 Accepted）后开始实现。

动机

现状。 0091 把应用层拆成 AppCore 与 AppUI 时，定下的分界是「UI 组件不许进 AppCore，UI 框架的模型可以」，并明确否决了「ViewModel 只输出不含 UI 类型的描述，属性串和图标交给 AppUI 渲染」，理由是「改写 cell ViewModel 的输出换不来更好的可测性」。结果是 AppCore 里有 31 个文件 import AppKit 或 UIKit：

  • cell ViewModel 的 Appearance 装着 NSImage 与 NSAttributedString（RuntimeObjectCellAppearance.swift:24-34、SidebarRootCellViewModel.swift:53-64、FindResultNode.swift:15-27、ReportCellViewModel.swift:17-23）；
  • ContentTextViewModel 的输出是上过主题的 NSAttributedString（ContentTextViewModel.swift:70-87,651-669），主题 ThemeProfile 的接口全是 NSUIColor / NSUIFont；
  • 剪贴板与 Finder 的真实实现直接写在 AppCore 里。

新的理由，三条，都能验证：

  1. 状态要能序列化。 Shopify Engineering 的《Reflex》（2026-11-05）描述了一种架构：每个 ViewModel 暴露一份可编码成 JSON 的状态和一组可调用的动作，agent 用 ls 看当前界面、用 do 执行动作，不渲染界面就能验证行为。RuntimeViewer 已经具备其中大半，缺的是状态本身是值：一个 NSImage 只能序列化成像素，一个 NSAttributedString 里是 NSFont、NSColor 对象。今天 agent 要验证一处界面改动，只能启动整个 App 再截图，而且会和用户正开着的 RuntimeViewer 抢 CLI host 与 MCP 端口。本提案只做「状态全是值」这一步，ls / do 本身另立提案。
  2. 0091 说的「换不来可测性」现在不成立了。 AppCore 的测试今天按对象身份比图标、按像素取样比颜色、逐段比字体（具体文件见前期调研）。换成描述值以后，这些断言都变成值的 ==，「画出来对不对」只在 AppUI 的测试里验一次。
  3. 正式构建每次显示都白建一份富文本。 SourceEditor 内容视图只读 .string、.link 和 .runtimeViewerDeclaredMember，从不显示上过色的串；可每次显示，ContentTextViewModel 都要建一遍带字体颜色的富文本，再整份拷成可变串加声明成员属性。把上色挪到只有 NSTextView 视图和 iOS 视图订阅的环节，这两步在正式构建上就没了。

提议方案

新的分界规则（替换 0091 的「边界标准」）

AppCore 可以用：Foundation 的值与工具类型（NSRange、NSString、NSLock、NSRegularExpression……）、CoreGraphics 的几何类型、RxSwift / RxCocoa 的 Driver / Signal、@RxObserved、Router。AppCore 不可以：import AppKit、UIKit 或 Cocoa；在代码里写出任何 AppKit/UIKit 的类型名；用 NSAttributedString。唯一的例外是 iOS 路由：DocumentState 里私有的 SelectionRouter 和 EmptyRouteTransitionContext 要满足 XCoordinator 的协议，必须写 UIViewController，这几行连同 import UIKit 记进边界测试的 allowedLines 并写明理由。

AppCore 产出描述值，AppUI 解析

AppCore 的描述值描述什么AppUI 怎么解析
IconDescriptor（封闭枚举）系统符号、镜像种类的符号、对象图标与字母徽章（Glyph）、Find 的六个行符号、引擎图标descriptor.image（带缓存），descriptor.image(size:) 给固定图标尺寸的地方
ColorDescriptor（封闭枚举）图标着色：secondaryLabel、tertiaryLabel、镜像种类的颜色descriptor.color
RowText（结构体）一行文字：若干段，每段一个语义角色，加可选字号rowText.attributedString(in: RowTextStyle)
ContentInterface（结构体）语义串、链接表、声明成员表、注释装饰、宏展开，以及一个 IDinterface.attributedString(themedWith:)，由 ContentTextRenderer 在后台调用

IconDescriptor 和 ColorDescriptor 用封闭枚举：AppUI 必须给每一种画出图来，加了新种类而 AppUI 没跟上时编译器报错。RuntimeImageKind.icon / iconColor / coloredIcon 和 RuntimeObjectIcon.icon(...) 一族以同样的名字搬进 AppUI 的扩展，App 里直接调它们的地方一行不用改。

内容页

  • ContentTextViewModel 不再知道主题：去掉 theme、attributedString；RenderedInterface 换成 ContentInterface。
  • 后台的「准备」一步只建旁表：链接表、声明成员表、注释装饰、宏展开，每个平台都建。
  • 加载转圈改成「从开始取接口，到视图报告显示完」：Input 新增 interfaceDisplayed: Signal<ContentInterface.ID>，没有默认值；收到同一 ID 的报告才结束等待，旧 ID 的迟到报告无效。上色的时间仍在转圈里，没有空档。
  • ContentTextRenderer（AppUI）在后台上色，主题变了就重新上色，并有自己的 delayedRendering 处理只换主题的情况；renderedText 是冷的，SourceEditor 视图只订阅 theme，一份富文本都不建。
  • 上色时只在 macOS 上写 .link（与今天一致）；不再写 .runtimeViewerDeclaredMember，右键菜单与光标成员改查旁表，下标都是 UTF-16 偏移。
  • 主题整体搬进 AppUI；SourceEditorThemeConversion 不用改。

跨层服务、修饰键、边界测试

  • PasteboardClient、FinderClient 改成 0091 的跨层写法，真实实现搬进 AppUI；两个 key 加进 CrossLayerDependencyTests。runtimeObjectIconRendering 整体搬进 AppUI，runtimeEngineIconProviding 删除，两者移出跨层清单。

内容页的渲染管线
  • 取接口：combineLatest → Observable.async 走接口缓存 → trackActivity(_commonLoading)。
  • 上色：在 userInitiated 后台队列上建富文本与 .link，再整份拷成可变串加声明成员属性；注释装饰与宏展开只用语义串。
  • 加载转圈：_commonLoading 盖住取接口与上色；delayedLoading 晚 100 毫秒发 true、立即发 false。
  • 主题来自 ResolvedThemeStream（macOS 依赖），唯一使用方是 ContentTextViewModel。
  • 只有 NSTextView 视图、它的行号尺与 iOS 视图读上过色的富文本；其余读者只要文字、链接目标或声明成员。
  • 链接目标的解析不需要 UI；MCP、批量导出、CLI、右键拷贝都用纯文本；FrozenSemanticString 是 Sendable。
图标、事件、系统服务、测试
  • RuntimeObjectIcon.Glyph 已经是值；0091 把绘制交给 AppUI，但 AppCore 仍自己调渲染、存 NSImage。
  • 引擎图标取决于 engine.source、hostInfo.metadata 与按 engineID（String）记下的图标；RuntimeEngineManager.runtimeEngines 汇总了它管理的全部引擎。
  • Find 行的图标按行的种类组合：字母徽章、对象图标、镜像种类图标，以及六个各有字号字重的固定符号。
  • 没有任何 AppCore 的 Input 收 NSEvent 或修饰键；视图控制器自己换成「在哪打开」。
  • 剪贴板与 Finder 的 live 值写在 AppCore；跨层写法与 CrossLayerDependencyTests 由 0091 定下。
  • 断言 UI 类型的 AppCore 测试约二十个文件；渲染没有基准测试，只有 content.attributedStringBuild 一个 signpost。
前人怎么做、验证过什么
  • Apple 的 ImageResource / ColorResource：Hashable, Sendable 的结构体只写资源名，由 UI 层解析；SwiftUI 的 Image(systemName:) 也是到渲染时才解析的描述。
  • Reflex：Core 模块不 import UIKit，状态编码成 JSON。
  • 本仓库：RuntimeObjectIcon.Glyph + runtimeObjectIconRendering。
  • 写作时没有构建或测量；「正式构建少建一份富文本」由第四步的测量确认。
  • 推测，第二步验证：runtimeEngines 包含 Report 与来源选择器显示的每一个引擎。

替代方案考量

展开
  • 维持 0091 的分界——否：状态不是值，测试仍按身份与像素断言。
  • 只改对外输出，内部照用 AppKit——否：这条边界没法用测试守住。
  • 只抽系统服务和修饰键——否：对目标没有帮助。
  • 富文本统一用 AttributedString——否：大接口每次多一次整串转换，内容页已有 FrozenSemanticString。
  • 主题留在 AppCore、换成平台无关值——否：AppCore 要多维护一套只为渲染服务的值类型。
  • 上色经跨层服务在 ViewModel 里调——否：状态里会多一个不透明、不能序列化的渲染结果。
  • 不加显示报告，只把两路转圈「或」起来——否：取接口与渲染之间有一个 runloop 的空档，转圈会闪一下。
  • IconDescriptor 写成结构体加静态成员——否：封闭枚举让 AppUI 漏画在编译期报错。
  • 引擎图标的描述值带一份引擎快照——否：元数据是否 Hashable 未查证，且快照会过期；备选是弱引用记录。
  • 为修饰键新造 OptionSet——否：换算本来就在视图层做。
  • 连同 Architectures 与 Settings 一起清——否，范围外。
  • 这次就做成 Codable——否：JSON 形状留给 ls / do 提案定。
