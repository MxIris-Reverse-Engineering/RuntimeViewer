摘要

Load Frameworks 不再把框架装进 My Mac 的 service。在 My Mac 的窗口里选了框架，App 新起一个 XPC service 实例（新的内嵌 service RuntimeViewerFrameworkService，每次一个，带 disable-library-validation），开一个挂在这个实例上的新窗口，把这次选的框架都加载进去；之后在这个窗口里再加载，也进同一个实例；没有窗口留在这个实例上时（关窗，或窗口换到别的来源），实例退出，框架随之卸载。

加载失败时窗口照常打开，内容区显示诊断：在加载失败的那个进程里模拟 dyld 的查找——依赖链、rpath 栈及其展开、每条候选路径的结果——并附上 dyld 原文；缺的依赖就在宿主 App 的 Frameworks 目录里时，提议先按绝对路径加载它们再重试，找不到时让用户指定宿主 App 或搜索路径；重试成功，窗口原地变成普通窗口。

窗口挂在 Mac Catalyst、注入进程、远端 Mac 等引擎上时，框架仍加载进那个进程，失败时同一诊断以 sheet 显示，不带重试与修复。诊断随失败的那次加载一起回来（加载请求多一个可选字段，旧版对端照旧只回 dyld 原文，App 据原文给出简化诊断），不给旧版 payload 发它不认识的命令。窗口的侧栏只列这次加载的框架和它们不在系统 shared cache 里的依赖；窗口不进 Open Recent，重启后不恢复。

方案

加载去哪，按窗口的引擎分

窗口所在的引擎框架加载到哪里失败时怎么显示
My Mac（.local）新起一个框架实例，开一个新窗口挂在它上面；原窗口不动新窗口的内容区显示诊断，带重试与修复
框架实例（.frameworkInstance）同一个实例，同一个窗口窗口还什么都没打开时在内容区；已经打开了内容时用 sheet。都带重试与修复
Mac Catalyst、注入进程、远端与 Bonjour、直连 TCP那个进程，与今天一样sheet 显示诊断，不带重试与修复
文件（.file）不可用，与今天一样—

My Mac 上不再保留「直接加载进 My Mac」的入口。工具栏按钮在 My Mac 窗口里的 tooltip 改为「在新的独立实例里加载框架」。侧栏镜像行的 Load、CLI 与 MCP 的加载不受影响。

框架实例

  • 新的内嵌 XPC service RuntimeViewerFrameworkService.xpc：_MultipleInstances，hardened runtime 加 disable-library-validation；0079 式外壳，活在 ServicePluginEntry.runFrameworkService()。
  • 一次 Load Frameworks 一个实例：以 .xpcService(.dedicatedInstance(…)) 连接，launch payload 只有实例的标识、名字和第一个框架的 URL，不列要加载的框架——崩溃后的重连得到空实例，不会重放会崩的加载。
  • 实例里的引擎：镜像来自本进程，目录换成 RuntimeFrameworkInstanceImageCatalog，只列经引擎加载的镜像（成功或失败）和随之带进来、不在 shared cache 里的依赖；每次加载后重建侧栏节点。
  • 系统镜像向 My Mac 借（0081 的借用方）；不开派生数据；照规则装 RuntimeInjection 与 RuntimeCrossReferences。
  • 生命周期：没有文档留在引擎上（.vacated）就立即结束，没有宽限期；实例崩溃时窗口进入「实例已停止」页，给「Load Again」，不自动重试。
  • 来源列表：活着时在「Isolated Frameworks」一节列出，别的窗口可以换上来；不分享给别的 Mac，CLI 不列。不进 Open Recent，重启不恢复。

框架实例的窗口

  • 来源名「Foo.framework (Isolated)」，多个时「Foo.framework + 2 (Isolated)」；工具栏副标题按状态显示「Loading…」「Couldn't Load」「Isolated」；图标是框架自己的。
  • 侧栏两个根节点：「Frameworks」（经引擎加载的，失败的也在，修复时先加载的依赖也在这里）与「Dependencies」（dyld 带进来的非 shared cache 镜像）。
  • 内容区：加载中显示「Loading Foo.framework…」；失败显示诊断页；全部成功后页面消失，焦点栏打开第一个框架的镜像页。窗口已经打开了内容时，之后的失败改用 sheet。

诊断

  1. 缺了什么、谁要它：从 dyld 原文解析出失败的种类——找不到镜像、找不到符号、镜像不兼容、其他。
  2. 依赖链：从要加载的框架沿 LC_LOAD_DYLIB 走到出问题的那条边（跳过弱链接与延迟初始化的依赖）。
  3. dyld 去哪里找了：按 rpath 栈逐行列出归属、原文、展开后的候选与结果，加一句「为什么」；另列 dyld 自己报的尝试列表。
  4. 能怎么修（只在框架实例里）。

修复

  • 自动提议：在框架所在的 App、指定过的宿主 App、加过的搜索路径里找缺的依赖；以宿主 App 的可执行文件作主程序、搜索路径作额外 rpath 重走一遍，全都找得到就给出方案（依赖在前）。
  • 执行：按绝对路径逐个加载这些依赖，再重试；dyld 解析 @rpath/… 时先匹配已加载镜像的 install name。
  • 找不到时：「Choose Host App…」「Add Search Path…」交给实例重新诊断，有方案就立即执行。
  • 用过的宿主 App 与搜索路径记到窗口关掉为止，不写进设置。

旧版对端

诊断由加载请求里的可选字段请求。旧版进程解码时跳过它，失败照旧只回原文；App 据原文解析出能解析的部分，诊断页标明对端是旧版。不给任何可能是旧版的对端发新命令；重新诊断的命令只发给框架实例。

设计中自定的假设

用户没有逐条定，写提案时按已定方向补齐，可以推翻

  • 其他引擎的窗口仍加载进原进程，失败用 sheet、不带重试（澄清提问时列过，未反对）。
  • 加载时崩溃不自动重试，给「Load Again」（同上）。
  • 新建专用 service，不复用 My Mac 的；系统镜像向 My Mac 借（同上）。
  • CLI 与 MCP 不加命令（同上）。
  • 宿主 App 与搜索路径只在窗口活着时记住（同上）。
  • 窗口开着时其他窗口的来源选择器也列出这个实例（同上）。
  • 已经打开了内容的框架实例窗口，之后的失败用 sheet；诊断不做成标签历史的一步。
  • 侧栏分「Frameworks」「Dependencies」；先加载的依赖算在「Frameworks」；失败的框架显示为未加载的行，不加原型里的「failed」角标。
  • 框架实例窗口的书签按第一个框架的路径归档。
  • open panel 照旧只收 .framework。
  • 诊断随失败的回复带回，不另发命令；重新诊断只发给框架实例。
  • iOS 的引擎管理里框架实例不可用。

非目标

  • CLI 与 MCP 不加命令；它们的加载照旧进各自的引擎（包括 My Mac）。
  • 侧栏的 Load 按钮、镜像页、路径栏的加载失败仍只显示文字（后续项）。
  • 不加载 dylib 或裸 Mach-O；不为 x86_64 框架起 Rosetta 实例。
  • 不修 My Mac 的进程目录「加载后不重建侧栏节点」那一处（未实测）。
  • 不在实例之间、启动之间记住宿主 App 与搜索路径；不恢复窗口，不进 Open Recent；崩溃后不自动重试。

详细设计

落点与「改动要聚合」
  • XPC 相关的代码只在根 AGENTS.md 列出的几处：FrameworkInstance/RuntimeFrameworkService.swift 与 RuntimeFrameworkServiceHost.swift，以及 ServicePluginEntry.runFrameworkService()；传输零改动。
  • RuntimeEngine 只改两处判断与 _loadImage 末尾一行，引擎只认识目录的 rootNodesFollowLoads。
  • 新 RuntimeSource case 碰到的穷举 switch 每处一行，集中在步骤 3；App 一侧的加载流程只在 FrameworkLoader。
Core：诊断的模型与命令 
public struct RuntimeImageLoadDiagnosis: Codable, Sendable, Hashable {
    public struct Failure { var kind: Kind  // open struct: imageNotFound, symbolNotFound,
                                            //   incompatibleImage, unrecognized
        var missingInstallName, symbolName, referencingImagePath, expectedInImagePath, reason: String? }
    public struct ChainLink { var imagePath, installName: String; var isResolved: Bool }
    public struct RpathSearch { var ownerImagePath: String; var role: Role  // mainExecutable,
                                                     //   dlopenCaller, loader, searchPath
        var rpath, candidatePath, outcome: String }
    public struct TriedPath { var path, reason: String }
    public struct Note { var kind: Kind  // rpathExpectsHostExecutable, dependencyInHostApplication,
                                         //   symbolMissingFromImage, architectureMismatch
        var imagePath, rpath, hostApplicationPath: String?; var architectures: [String]? }
    public struct Remedy { var hostApplicationPath: String?; var searchPaths: [String]
        var imagePathsToLoadFirst: [String] }
    public var imagePath, dyldMessage: String
    public var failure: Failure
    public var dependencyChain: [ChainLink]
    public var rpathSearches: [RpathSearch]
    public var triedPaths: [TriedPath]
    public var notes: [Note]
    public var remedy: Remedy?
    public var processArchitecture, operatingSystemVersion: String?
    public var isFromMessageOnly: Bool
    public init(dyldMessage: String, imagePath: String)  // older peers
}

public struct RuntimeImageLoadError: Error, LocalizedError, CustomStringConvertible, Codable {
    public var dyldMessage: String
    public var diagnosis: RuntimeImageLoadDiagnosis?
}

/// Encodes as an empty object when the load succeeded, as RuntimeEngineEmpty did.
public struct RuntimeImageLoadResponse: Codable, Sendable {
    public var failure: RuntimeImageLoadError?
}

struct LoadImageCommand: RuntimeEngineCommand {
    typealias Response = RuntimeImageLoadResponse
    let path: String
    var reportsFailureDiagnosis: Bool?   // skipped by older peers
}

/// Answered by the process that tried the load; sent only to framework instances.
struct DiagnoseImageLoadCommand: RuntimeEngineCommand {
    typealias Response = RuntimeImageLoadDiagnosis
    let imagePath, dyldMessage: String
    let hostApplicationPath: String?
    let searchPaths: [String]
}

extension RuntimeEngine {
    public nonisolated var diagnosesImageLoadsOnRequest: Bool
    public func diagnoseImageLoad(at imagePath: String, dyldMessage: String,
        hostApplicationPath: String? = nil, searchPaths: [String] = []) async throws
        -> RuntimeImageLoadDiagnosis
}
Core：诊断算法
  1. DyldLoadFailureMessage(parsing:) 解出失败与 tried: 列表。
  2. rpath 栈的底是主程序的 LC_RPATH，然后是调用 dlopen 的镜像的。从磁盘读要加载的镜像（胖文件取本进程 CPU 的切片，取不到即「镜像不兼容」），深度优先沿非弱链接、非延迟初始化的依赖走，每进一层把加载者的 rpath 压栈；一条边先按 install name 匹配已加载的镜像，再用 DylibPathResolver.resolution(…) 逐条展开。第一条解析不了的边（原文里有 Referenced from 时优先找那一条）就是依赖链的终点。
  3. 那条边是 @rpath/… 时，每一次尝试成为 RpathSearch 的一行；@executable_path 开头的 rpath 出现在非主程序的镜像上时，加一条说明。
  4. 修复方案：宿主 App 候选依次是指定的与路径上最近的 .app；以它的可执行文件作主程序、搜索路径作额外 rpath 重走整棵依赖树。原本解析不了、换了环境能解析的镜像按「依赖在前」排好就是 imagePathsToLoadFirst；还有解析不了的就不给方案。
  5. 缺符号时只给依赖链与说明，不给方案。

调研

现状代码与问题
  • 入口只有工具栏按钮；MainViewModel.swift:189-209 逐个 loadImageInServingProcess，失败弹 NSAlert；只有文件引擎不可用。
  • LoadImageCommand 的回复是 RuntimeEngineEmpty；最终进程 dlopen，失败抛 DyldOpenError(message: dlerror())。
  • 错误过线只剩文字（XPC 是 localizedDescription，socket 是 String(describing:)），所以诊断只能放在回复里。558b6abf 让原文过得来。
  • 加载后 reloadLocalData(isReloadImageNodes: false) 不重建节点，My Mac 加载的非 shared cache 框架大概率不出现在侧栏（读代码所得，未实测，本提案不修）。
  • 没有任何持久化：Document 不读不写，不恢复窗口，Open Recent 只由 FileController 显式登记。
照搬文件模式的多实例 service
  • 外壳、xcconfig、bundle identifier、App 的 Info.plist 键、工程与 Tuist 的接线都有现成的一套。
  • .dedicatedInstance 中断后以新连接、新实例、同一份 payload 重连，所以 payload 不能列框架。
  • local service 已经带 disable-library-validation；file service 有意不带。
  • 文件引擎关窗后停 30 秒再挂起；框架实例要立即结束。
  • 0081 只给 system 与 attached 分配 owner，文件引擎不借；框架实例借得了。
dyld 的事实（dyld-1323）
  • dlerror() 的内容就是控制台里的 Library not loaded / Referenced from / Reason: tried:。
  • DYLD_PRINT_SEARCHING 只在启动时读、要 AMFI 放行，没有 API 取得到。
  • dlopen_preflight 只查顶层架构切片。
  • rpath 栈：主程序 → 调用 dlopen 的镜像 → 依赖链；@executable_path 展开到 service 自己。
  • 解析 @rpath/… 先匹配已加载镜像的 install name，所以先加载依赖可行——读源码可行，未实测，步骤 1 先实测。
现成的 Mach-O 能力与兼容规则
  • DylibPathResolver 已按 dyld 规则展开三种 @ 路径，尝试只写日志；dependencyEntries 按 dyld 顺序累积 rpath。
  • MachODependencies 不展开 @ 路径，不用。
  • 引擎之间不交换版本；经 Mach service 的旧版 payload 收到不认识的命令会断开（PR121.73）。§4.4：请求加可选字段、回复的新形状只给声明读得懂的请求方。

替代方案

12 条，均已否
  • 保留加载进 My Mac，只加诊断：用户否，问题正在 My Mac 上。
  • 所有窗口共用一个长期实例：卸不掉，崩溃牵连所有窗口。
  • 用文件模式打开框架：file service 只读不运行；Load Frameworks 要真的运行。
  • payload 列出框架、由实例启动时加载：崩溃后同一份 payload 起新实例，陷入崩溃循环。
  • 设 DYLD_FRAMEWORK_PATH：hardened runtime 要另一个 entitlement，XPC service 的环境变量不能按实例给；留作预加载不成立时的退路。
  • 新命令发给所有引擎：旧版 payload 会断开（PR121.73）；改为随回复带回。
  • 在 App 进程里诊断：rpath 栈取决于失败的进程，远端文件不在本机；用户定在失败的进程里。
  • 用 MachODependencies：不展开 @ 路径。
  • 用 dlopen_preflight：不查依赖。
  • 读 DYLD_PRINT_SEARCHING：取不到。
  • 崩溃自动重试：用户定不重试，与 0037 一致。
  • 诊断页做成标签历史的一步：改动面大、Back 会走进失败页、关标签即丢；改用空栏页面加 sheet。另：关窗后像文件引擎一样留 30 秒也否——恢复要重跑构造函数。

影响

用户可见变化

  • My Mac 里点 Load Frameworks 开新窗口「Foo.framework (Isolated)」；跳到系统类型照常可用（数据来自 My Mac），也可以把新窗口换回 My Mac——那样实例会结束。
  • 加载失败显示诊断页或带诊断的 sheet，不再只有原文。
  • 来源选择器多一节「Isolated Frameworks」；这类窗口不进 Open Recent、重启不恢复。

可发现性

入口不变，tooltip 说明会开新的独立实例；修复提议直接在诊断页横幅上；没有开关。

数据与配置兼容

不改设置、不迁移。书签多一种归档身份，旧版读到时跳过。新来源不发给对端，步骤 3 核对不进持久化。LoadImageCommand 加可选字段，回复在线上仍是空对象。

平台与最低版本

只在 macOS 上，最低版本不变。每个独立窗口多一个进程，常驻内存未测，步骤 8 实测后补进提案。

发布

新 service 与 local service 一样带 hardened runtime 与 disable-library-validation，公证照常；SKIP_INSTALL = YES；正式发版前在 Distribution workspace 归档并公证一次。不影响 Sparkle。

落地步骤

  1. 诊断本身（Core，无界面）：先跑 PreloadSatisfiesRpathDependencyTests，不通过就停下回来重议。行为：解析三种原文与未知原文；依赖链终点；rpath 行按 dyld 顺序；@executable_path 的说明；推断宿主 App；修复方案依赖在前；搜索路径；找不到时没有方案；已加载镜像按 install name 算存在；resolve 结果不变。
  2. 诊断随失败的加载过线：三种传输都带回诊断；冻结的旧服务端只有原文；冻结的旧请求方回复逐字节不变；中转原样转发；Mach service 的 XPCEncoder 跳过字段；新命令不发给其他引擎；路由声明为 Neither。
  3. 框架实例的 Core 与传输：来源的身份与不分享；书签原始值往返；凭证与 payload；host 的侧栏两节、失败的也列、基线与 shared cache 不列、每次加载重建节点；进程目录行为不变。核对 RuntimeSource 的编码处。
  4. 内嵌 service：Debug-arm64e 与 Release 构建，核对嵌入、签名、外壳大小、不链接包；./TuistScript.sh check 通过。
  5. 引擎管理：列在「Isolated Frameworks」；结束后拿掉；借 My Mac；不分享；CLI 不列；没有内嵌 service 时起不来。
  6. App 的加载流程与页面的值（AppCore）：四种引擎分流；按顺序加载并记 Manual Loading；停在第一个失败、修好后接着加载；修复先加载依赖；窗口记住宿主 App；旧版对端简化诊断；实例停止不重试、Load Again 从头加载；空窗口成功后打开镜像页；有内容时走 sheet；retirement 只管框架实例；页面文字与拷贝内容。
  7. App 的窗口、路由与页面：开窗口建在新实例上；空栏进出 frameworkLoad 场景；失败路由弹 sheet。
  8. 文档、实测与收尾：用真实的第三方 App 框架走一遍失败 → 修复 → 成功；关窗后没有残留进程；注入进程窗口的 sheet；测一个实例的常驻内存；按改动地图更新文档；判断实现说明与术语。
