摘要

导出（单个镜像的 Export Interfaces… 与批量导出）在 Objective-C、Swift 之外写出镜像的 C++ 类与命名空间。每个 C++ 对象写成一份伪头文件，内容就是内容区打印的那一份。目录格式放进 CPlusPlusHeaders/，单文件格式合成 <镜像名>.hpp，两种格式在配置页里像 ObjC、Swift 一样单选。

C++ 对象是一棵树：顶层多是命名空间，类挂在下面，而打印器打印命名空间时只给其中的类写一行前向声明。所以导出要把整棵树展开，每个类与命名空间各写一份。文件名用限定名，免得不同命名空间里的同名类互相覆盖。

Core 的导出配置加一个默认关闭的 includesCPlusPlusObjects，只有 App 的两条导出路径打开它，所以 CLI 的 export 子命令输出不变。

提议方案

  1. Core 的导出配置加两项：includesCPlusPlusObjects: Bool（默认 false）与 cPlusPlusFormat: Format（默认 .directory）。默认不要 C++，所以 CLI 和现有调用点的行为不变。
  2. 要 C++ 时把树展开：exportInterfaces 取对象时把字段带上，再把每个对象换成它的 exportedObjects：ObjC、Swift、C 对象只有自己；C++ 对象是自己加上全部后代，深度优先、父在前，顺序与侧栏一致。配置页数 C++ 对象时用同一个。
  3. 写出分三组：Objective-C（含 C）、Swift、C++。C++ 的单文件是 <镜像名>.hpp，目录是 CPlusPlusHeaders/。写出器改成按组的表来写，重复的写出代码合成一段。
  4. C++ 的文件名用限定名：沿用现有的清洗规则，非法字符（含冒号）一律换成下划线，所以 std::exception → std__exception.hpp。全局命名空间写成 GlobalNamespace.hpp。
  5. 结果与 README：结果加 cPlusPlusCount；README 只在要了 C++ 时多 C++ format 与 C++ interfaces 两行；C++ 没有生成选项，不加选项一节。
  6. App 的两条导出路径都要 C++：单个导出的配置页在镜像里有 C++ 时显示「C++:」一组单选，摘要多「N C++」，完成页加「C++: N」；批量导出一直显示 C++ 一组，完成页卡片改成三个数。C++ 格式存在 Exporting.cPlusPlusFormat，两者共用，默认 Directory。
  7. 不加「不导出 C++」的开关：ObjC 和 Swift 也没有，镜像里有就导出。
非目标
  • CLI 的 export、MCP、Find 照旧看不到 C++ 对象；提案索引的暂缓项改为只列这三项。
  • 不改 C++ 打印器：导出的就是内容区的文本，命名空间里的类照旧是前向声明。
  • ObjC、Swift 的导出不变：仍只导顶层对象，文件名和目录都不变。
  • 不按命名空间分子目录（替代方案第 3 条，用户定了平铺）。

详细设计

Core 的 API 
public struct RuntimeInterfaceExportConfiguration: Sendable {
    public let cPlusPlusFormat: Format
    /// Whether the export asks for the image's C++ objects
    /// (`objects(in:includesCPlusPlusObjects:)`) and writes them. Off by
    /// default, so a caller that predates C++ objects exports what it did.
    public let includesCPlusPlusObjects: Bool

    public init(
        imagePath: String,
        imageName: String,
        directory: URL,
        objcFormat: Format,
        swiftFormat: Format,
        cPlusPlusFormat: Format = .directory,
        generationOptions: RuntimeObjectInterface.GenerationOptions,
        includeMetadata: Bool = true,
        includesCPlusPlusObjects: Bool = false
    )
}

extension RuntimeObject {
    /// The objects an export writes for this one: itself, and for a C++
    /// class or namespace every class and namespace declared in it, depth
    /// first.
    public var exportedObjects: [RuntimeObject] { get }
}

public struct RuntimeInterfaceExportResult: Sendable, Equatable {
    public let cPlusPlusCount: Int
    public init(succeeded:failed:totalDuration:objcCount:swiftCount:cPlusPlusCount: Int = 0)
}

struct RuntimeInterfaceExportItem: Sendable {
    enum Group: CaseIterable, Sendable {
        case objectiveC   // .objc and .c:  ObjCHeaders/,      <image>.h
        case swift        //                SwiftInterfaces/,  <image>.swiftinterface
        case cPlusPlus    //                CPlusPlusHeaders/, <image>.hpp
    }
    var group: Group { get }
}
exportInterfaces 的流程 
let objects = try await objects(in: configuration.imagePath,
                                includesCPlusPlusObjects: configuration.includesCPlusPlusObjects)
    .flatMap(\.exportedObjects)
// per object, as before: interface(for:options:), empty → skipped, failure → counted
// count per group (objcCount, swiftCount, cPlusPlusCount)
for group in RuntimeInterfaceExportItem.Group.allCases {
    let items = results.filter { $0.group == group }
    guard !items.isEmpty else { continue }
    try RuntimeInterfaceExportWriter.write(items, as: group, format: configuration.format(for: group),
                                           to: configuration.directory, imageName: configuration.imageName)
}

三组的写出顺序与今天相同（ObjC 在 Swift 前面），C++ 最后。单文件格式是各对象界面按展开顺序拼接，中间空一行。

C++ 的文件名
限定名文件名
std::exceptionstd__exception.hpp
(anonymous namespace)::Foo(anonymous namespace)__Foo.hpp
std::__1::vector<int, std::__1::allocator<int>>std____1__vector_int, std____1__allocator_int__.hpp
::（全局命名空间）GlobalNamespace.hpp

清洗规则沿用现有的（/:<>"\|?* 换成 _，超过 255 字节时截断并加哈希），只是 C++ 的输入从 displayName 换成了 name。全局命名空间里一个真叫 a__b 的类会和 a::b 撞；这种名字是留给实现的保留名，按现状处理，不另做去重。

调研

  • 单个导出的配置页用不带参数的 objects(in:)（ExportingConfigurationViewModel.swift:57-67），进度页组配置调 exportInterfaces（ExportingProgressViewModel.swift:51-90）；批量导出在 BatchExportingProgressViewModel.exportOne（:164-260）里逐个镜像调同一个入口。
  • CLI 的 export（CommandExecutor.swift:438-451）也走 exportInterfaces；MCP 没有导出。
  • Core 的导出只取顶层对象，按 isSwift 分两组（RuntimeEngine+Export.swift:15-145）；写出器里又各分一次组，两组的写出代码几乎逐行重复。
  • 0103 已给导出补了 C++ 的臂（.hpp），但 C++ 的 isSwift 是 false，要是进来会落进 ObjC 那一组。
  • C++ 对象的 name 是限定名、displayName 是最后一段；打印器对其中声明的类型只写一行前向声明（CPlusPlusInterfacePrinter.declaredSection，:360-381）。
  • 耗时（0103「实测」）：Espresso 进程内建 C++ section 约 0.25 秒、cache 文件约 1.9 秒；给 4,379 个类的 56,204 个槽位取名 0.62 秒 / 2.43 秒。
  • 旧版对端收到带字段的请求时只回 ObjC 与 Swift（ObjectsInImageCPlusPlusWireTests），导出照常、没有 C++ 文件。

替代方案

六条，都没有采用
  1. 只导顶层 C++ 对象：顶层几乎全是命名空间，类等于没导出。否决。
  2. 每个顶层命名空间一个文件、把类展开写进去：要给打印器加一种打印方式，导出与内容区就不一致了。否决。
  3. 目录格式按命名空间分子目录：浏览起来更顺手，但命名空间自己的文件放哪、类里嵌套的类怎么放、模板参数里的 :: 怎么办，都要另定规矩。用户定了平铺。
  4. 导出一律带 C++：会悄悄改掉 CLI 的输出，CLI 的插件 skill 和版本也得跟着改。否决。
  5. 配置页加「Include C++」勾选框：ObjC 和 Swift 都没有，C++ 的代价也小。不加。
  6. 用 cPlusPlusFormat: Format? 同时表达要不要与格式：nil 的意思要读文档才知道。否决。

影响

  • 用户可见：导出带 C++ 的镜像时，多出 CPlusPlusHeaders/ 或 <镜像名>.hpp；配置页和完成页多了 C++ 的格式与计数。
  • 可发现性：单个导出时，镜像里有 C++ 才出现 C++ 一组；批量导出一直显示；release note 写一句。
  • 兼容：新的 UserDefaults 键 Exporting.cPlusPlusFormat，没有时取 Directory；线上协议不变；新参数都有默认值，CLI 和现有测试不用改。
  • 平台：导出只在 macOS 上有，iOS 不涉及。
