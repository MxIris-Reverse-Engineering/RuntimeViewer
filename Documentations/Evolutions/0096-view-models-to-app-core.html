0096 - macOS App 的 ViewModel 移进 AppCore，通用视图移进 RuntimeViewerUI

摘要

macOS App target 里还有 18 个 ViewModel 文件，以及它们的路由与状态类型。这次把它们全部搬进 RuntimeViewerAppCore，并把其中用到的 UI 类型改成 AppCore 的值：

  • 主窗口的工具栏活动、来源选择器的内容与图标、标题图标、历史菜单。
  • 特化页的描述文字。
  • 「在 Finder 中显示」与拷贝。

MCP 状态弹窗通过新的跨层服务 mcpServerClient 启停服务，接口在 AppCore，真实实现在 MCP 包。没人用的 Load Frameworks 删掉。8 个不碰 AppCore 类型的通用视图搬进 RuntimeViewerUI。

此后 App target 只放 ViewController、window controller、coordinator、生命周期控制器、绑着 AppCore 类型的视图与菜单胶水。新增的 AppTargetBoundaryTests 发现 App 里有 ViewModel 就失败。行为不变，没有用户可见的变化。

访问级别与平台条件

搬进 AppCore 的文件整体包在 #if os(macOS) 里，与今天的 SpecializationViewModel.swift 相同，所以 iOS App 自己的 MainViewModel / MainRoute 不受影响。App 要读的成员改 public，各 Input 补 public init，以编译器报错为准补齐。新目录名不带空格：AttachToProcess/、GenerationOptions/、Exporting/、MCP/、Main/、RuntimeSourcePicker/、Specialization/。

防回流检查

AppTargetBoundaryTests 用 PackageSourceScan（新加读任意目录的入口）读 RuntimeViewerUsingAppKit/RuntimeViewerUsingAppKit/，注释与字符串不算。遇到名字以 ViewModel 结尾的类型，或继承 ViewModel<…>、CellViewModel、遵循 ViewModelProtocol 的类型，就报 文件:行；目录不在预期位置时直接失败。

工具栏活动为什么要在 AppCore 产出显示值

节流作用在显示状态上。挑选结果里有下次重挑的时间，到点重挑时显示可能不变；如果按挑选结果节流，一次不改显示的重挑也会占掉 1 秒窗口，把紧接着的真实变化推后。所以 AppCore 产出与 ToolbarActivityState 一一对应的值，在它上面去重、节流。ToolbarActivityState 本身留在 RuntimeViewerUI，因为接收它的视图在那里，而 RuntimeViewerUI 看不到 AppCore。

通用视图的判据

不依赖 AppCore、AppUI、Architectures、Core 与 App 类型的进 RuntimeViewerUI（8 个）。嵌在 VC 里的私有小视图按 App 的规则留在原处；RuntimeViewerSymbols（App 的 asset catalog）、SFSymbols+ReportNavigator（符号名）、EditorPaneContent（点名 App 的 VC）、RemoteProcessItemSource（绑引擎的选择器胶水）留在 App。搬文件不用改 Tuist 描述；原生工程只有行号标尺一条单文件条目要删。

替代方案考量

  • ViewModel 进 AppUI——否：AppUI 链接 UI 库，与「不链 UI 就能测」相反。
  • 绑着 AppCore 类型的视图也挪走——否：用户定留在 App。
  • MainViewModel 先留在 App——否：用户定一起迁。
  • ToolbarActivityState 搬进 AppCore 或另起共享模块——否：接收它的视图在 RuntimeViewerUI；只为两个值类型多一个模块不值。
  • 节流留在 AppUI——否：挑选与节流会分到两层，或改变时机。
  • 设备进程图标以图像数据进 AppCore——否：AppCore 存它只为原样交回。
  • MCP ViewModel 留在 App——否：用户定走跨层服务。
  • 跨层服务的实现放 App——否：包测试核对不到。
  • 只靠 AGENTS.md 防回流——否：用户定加测试。
  • 生命周期控制器的非 UI 逻辑一起抽——否：用户定不动。
