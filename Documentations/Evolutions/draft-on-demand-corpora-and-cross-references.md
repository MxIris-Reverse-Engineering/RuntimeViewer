# Draft - 语料与交叉引用表只常驻用得着的部分

- **状态**: In Progress
- **创建日期**: 2026-11-01
- **最后更新**: 2026-11-01
- **所属愿景**: 无
- **实现分支 / PR**: `feature/on-demand-corpora-and-cross-references`（从 `feature/engine-resident-memory` 切出：那条分支还没合进 `next`，本提案叠在它上面）

## 摘要

[降低引擎进程的常驻内存](draft-engine-resident-memory.md)之后，两个引擎进程里 Find 语料与交叉引用表仍占约一半：Mac Catalyst 引擎 215 MB 与 201 MB，My Mac 引擎 142 MB 与 127 MB（2026-11-01，Debug 版）。两者都是「每个已索引镜像一份、全部常驻」，而语料在磁盘上的派生数据只有内存里的十分之一，读回一份在 Release 版里只要 0.16～0.32 秒。本提案改成只常驻用得着的部分：语料只留最近搜过的、默认 64 MB，派生数据里存着的语料不在内存里也算建好，搜索时从派生数据读回来搜；交叉引用表默认 64 MB，按 Always Index 的顺序预建到装满为止，其余镜像在第一次查询时现扫，最近用过的留下。

## 方案

**语料**（`RuntimeInterfaceCorpusStore`）
1. 默认驻留上限从 256 MB 改为 64 MB（`defaultResidentByteLimit` 与 Settings › Search 的默认值）。
2. 派生数据里存着的语料，不论在不在内存里都算建好（仓库新增 `storedCorpora`，记每个镜像存着的 transformer 与摘要）：覆盖情况报 `.built`，搜索摘要不把它报为未建好，Find 不会为它请求构建。
3. 每次读派生数据都先只读摘要段（`RuntimeDerivedDataStore.read` 新增 `sections:`，容器只校验、解压要的段），放得进剩下的空间才读整份语料。所以构建与启动时的读回不会把放不下的语料整份读进内存；这些镜像建好了，但只有摘要在内存里。
4. 搜索按路径顺序逐个镜像读：在内存里的直接搜，不在的当场从派生数据读回来搜，一次只读一个。读回的语料搜完后，若把「这次搜索开始前搜过的」已存镜像按最久没搜过的顺序淘汰能腾出地方，就留下它；这次搜索读过的不淘汰（同样新），存不了派生数据的也不淘汰。这样搜全部镜像时的峰值是「常驻部分 + 正在搜的一个镜像」。
5. 构建与读回只填剩下的空间，不淘汰任何语料：打印出的语料先放进内存（马上能搜）、写进派生数据，写成了再看放不放得下，放不下就只留在磁盘上；读回的同理。存不了派生数据的语料（共享缓存以外的镜像、打印出了本进程地址的）照旧一定留下，为它先淘汰存着的、再淘汰其余的，各按最久没搜过的顺序。
6. 启动时 Always Index 的提前读取（`restore(imagePaths:transformer:)`）改成按给定的顺序一个一个读：放得下的整份读进内存，装满之后只读摘要。
7. 读回失败（文件被删、校验不过）的镜像不再算建好，并记一条失败，Report 能看到原因。
8. 推出（Report 里 Searchable Interfaces 的推出按钮）改用新调用 `RuntimeEngine.evictResidentInterfaceCorpora()`：只清内存，派生数据里存着的语料仍然建好、下次搜索读回；存不了派生数据的照旧清掉。线上沿用 `evictInterfaceCorpus` 命令，加一个可选字段 `keepsStoredCorpora`，老的对端不认识它，照旧全部清掉。

**交叉引用表**（`CrossReferenceSession`、`CrossReferencePreparationCoordinator`）
9. 默认驻留上限从 256 MB 改为 64 MB（Settings › Search 的 Cross References 一节，以及会话在收到任何上限之前用的默认值）。
10. 预建请求的选项加 `evictsNothing`：只在剩下的空间放得下时留下，不为它挤掉任何已留下的；结果加 `isKept`（留下了没有）。这样预建出来却没留下的镜像，分析器为它读的名字当场释放。一个预建被多个请求共享时，只要有一个请求（等着的查询）没要求 `evictsNothing`，就照旧按最近使用留下。两个字段在线上都是可选的：老的对端照旧按最近使用淘汰，老的结果读作「留下了」。
11. Keep Cross References Ready 的后台预建都带 `evictsNothing`。一次请求多个镜像时（开关打开、新进程、腾出了空间），Always Index 的镜像按它们在列表里的顺序排在前面（协调器从后台索引那里记下解析出的顺序），其余按路径。第一个回来「没留下」的镜像让预建停下：还开着的请求全部撤回，之后不再请求，直到有东西腾出空间——改上限、推出、重新打开开关、引擎换了新进程。Report 的历史里把它记成「Not Kept」。
12. 查询现扫时顺带预建的镜像照旧按最近使用留下，会挤掉最久没用的。

**设置**
13. 两个默认值改为 64 MB。旧的设置文件每次保存都写全部字段，所以文件里的 256 分不清是不是用户改的：`Settings.Search` 新增 `residentLimitDefaultsRevision`（缺省 0），`SettingsAccess.load()` 遇到 0 时把仍是 256 的上限改成 64、记成 1，以后用户再设成 256 也不会被改。

**没有询问就采用的假设**
- 已有设置文件里两个上限若仍是旧默认值 256，视为没改过，升级后改成 64；改过的保留。
- 推出按钮：清掉常驻部分，派生数据里的语料不受影响，搜索时照样读回。
- 读回的语料不另记 Report 行：读回只在搜索里发生，Report 的 Searchable Interfaces 行的大小反映的是常驻部分。
- 没有派生数据的引擎（App 进程内的 Bonjour 引擎、CLI 独立 host、测试）照旧只搜常驻的语料，只是上限变小。

**不做**
- 把语料压缩后留在内存里：省得没有读盘多，搜索还得每次解压。
- 交叉引用表存盘：[0061](0061-derived-data.md) 已决定不存（Release 版预建一个镜像只要零点几秒），本提案不推翻。
- 搜索时预读下一个镜像（读与搜重叠）：会让峰值多一个镜像，先不做，等实测读回耗时再定。

**落地步骤**
1. [x] 语料：上限默认值、存着的语料算建好、只读摘要的读取、搜索时逐个读回、构建只填剩下的空间、存不了的先淘汰存着的（测试：`RuntimeInterfaceCorpusDerivedDataTests` 的「Reading back on demand」一组，容器与派生数据仓库各一条部分读取的测试）。
2. [x] 语料：启动时按顺序读到装满为止；读回失败记失败；推出只清内存（测试同上，以及 `EngineDataEjectTests` 新增一条）。
3. [x] 交叉引用：`evictsNothing` 与 `isKept`（线上兼容测试）、协调器按 Always Index 的顺序预建到装满为止、Report 的「Not Kept」（测试：`CrossReferencePreparationTests` 两条、`CrossReferencePreparationFillTests`）。
4. [x] 设置：两个默认值改为 64 MB、旧默认值迁移、Settings 页的说明同步（测试：`SettingsResidentLimitMigrationTests`）。
5. [ ] 文档与实测：`AGENTS.md`、`Documentations/DerivedData.md`、术语表已同步；按 2026-11-01 的配置重测两个引擎进程，等用户跑 Debug 版。

## 决策日志

| 日期 | 决定 | 理由 |
|------|------|------|
| 2026-11-01 | Created as Draft | 推出按钮做完后实测，两个引擎进程里语料与交叉引用表仍占约一半；用户选择改成按需常驻，并另查 App 进程那次 699 MB 的峰值（不在本提案）。 |
| 2026-11-01 | 语料只留最近搜过的、默认 64 MB，其余搜索时从派生数据读回 | 用户在「留最近搜过的 64 MB」与「一个都不留、每次搜索都读」之间选了前者：反复搜同一批镜像不读盘，搜全部镜像时多出的读盘在 Release 版约 0.5 秒。 |
| 2026-11-01 | 交叉引用表默认 64 MB，按 Always Index 的顺序预建到装满为止 | 用户在「64 MB 装满为止」「默认关掉预建」「128 MB」之间选了第一个。只调低上限而照旧预建全部镜像的话，后建的会把先建的挤掉，后台白扫一遍，所以要改成装满就停。 |
| 2026-11-01 | 用户批准，开始实现 | 提案随功能分支的第一个提交走：`next` 上有上一篇功能在本地合进来、还没推送的提交，提案不能单独推到 `next`。 |
| 2026-11-01 | 派生数据里存着的语料不在内存里也算建好 | 否则每个被淘汰的镜像都会被 Find 当成未建好、请求重建，构建又把它读回内存，等于没省。 |
| 2026-11-01 | 每次读派生数据先只读摘要段，原第 1、2 步合成一处实现 | 覆盖情况与 Report 要每个镜像的摘要；只读摘要，启动与建索引时就不必把放不下的语料整份读进内存再扔掉——那样峰值不降，释放的内存也多半留在进程里。 |
| 2026-11-01 | 读回的语料只淘汰这次搜索开始前搜过的 | 搜全部镜像时若按纯粹的最近使用淘汰，每读回一个就挤掉一个，搜完留下的只是路径排在最后的几个，下次搜索全部重读。 |
| 2026-11-01 | 构建与读回只填剩下的空间，不淘汰 | 留哪些交给搜索决定；构建按索引顺序一个个完成，若能淘汰，留下的只会是最后建完的几个。 |
| 2026-11-01 | 推出改为只清内存，线上给原命令加可选字段而不是新命令 | 存着的语料不占内存，推出后仍应能搜；可选字段让老的对端照旧全部清掉，不至于报未知命令。 |
| 2026-11-01 | 同一文件同时只读一次，读别的段的请求等前一次读完 | 读取标记是「这个进程正在读这个文件」，两个读取并行时后一个会把前一个的标记当成残留删掉；原先按文件合并读取，摘要读取与整份读取的值类型不同，合并会让其中一个拿到空值。 |
| 2026-11-01 | 读回失败的镜像记一条失败 | 文件可能被设置里的「删除派生数据」删掉；记成失败，Report 能看到原因，再次请求即重建。 |
| 2026-11-01 | 交叉引用用请求选项 `evictsNothing` 与结果 `isKept`，第一个没留下的镜像就停 | 预建出来之前不知道多大，只能建完再判断；停下时撤回还开着的请求，浪费最多是同时在扫的那几个。没留下的镜像当场释放分析器为它读的名字，否则它们要等 64 个镜像的函数表攒满才放。 |
| 2026-11-01 | 设置迁移的状态存在设置文件里（`residentLimitDefaultsRevision`），不用 UserDefaults 标记 | 状态和它管的值在同一个文件里，换文件、重置设置都一致；主题迁移用 UserDefaults 是因为旧数据本来就在那里。 |
| 2026-11-01 | 协调器的集成测试接受「预建了但没留下」 | 测试进程里只有一个交叉引用会话，同时运行的测试套件也在里面预建；不挤掉别人之后，能不能留下取决于它们留下的空间。确定性的行为由脚本化对端的 `CrossReferencePreparationFillTests` 测。 |
