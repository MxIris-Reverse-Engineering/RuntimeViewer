# Draft - 语料与交叉引用表只常驻用得着的部分

- **状态**: Accepted
- **创建日期**: 2026-11-01
- **最后更新**: 2026-11-01
- **所属愿景**: 无
- **实现分支 / PR**: `feature/on-demand-corpora-and-cross-references`（从 `feature/engine-resident-memory` 切出：那条分支还没合进 `next`，本提案叠在它上面）

## 摘要

[降低引擎进程的常驻内存](draft-engine-resident-memory.md)之后，两个引擎进程里 Find 语料与交叉引用表仍占约一半：Mac Catalyst 引擎 215 MB 与 201 MB，My Mac 引擎 142 MB 与 127 MB（2026-11-01，Debug 版）。两者都是「每个已索引镜像一份、全部常驻」，而语料在磁盘上的派生数据只有内存里的十分之一，读回一份在 Release 版里只要 0.16～0.32 秒。本提案改成只常驻用得着的部分：语料只留最近搜过的、默认 64 MB，搜索时放不下的镜像从派生数据读回来搜；交叉引用表默认 64 MB，按 Always Index 的顺序预建到装满为止，其余镜像在第一次查询时现扫，最近用过的留下。

## 方案

**语料**
1. 默认驻留上限从 256 MB 改为 64 MB（`RuntimeInterfaceCorpusStore.defaultResidentByteLimit` 与 Settings › Search 的默认值）。超出时仍按「最久没被搜过」整镜像淘汰，但先淘汰派生数据里存着的镜像：它们随时能读回来；存不了派生数据的镜像（共享缓存以外的，例如经 Load Frameworks… 加载的框架）尽量留着。
2. 搜索读到一个已索引、不在内存里、但派生数据里有当前 transformer 的语料的镜像时，当场读回来搜（`RuntimeInterfaceCorpusStore.readStoredCorpus(from:imagePath:transformer:)`，含它现有的校验与读后遍历）。一次只读一个镜像、搜完再看要不要留：按最近搜过的顺序装进上限，装不下就丢掉。这样搜全部镜像时的峰值是「常驻部分 + 正在搜的一个镜像」（最大的 UIKitCore 约 90 MB），而不是全部语料。
3. 搜索摘要里，这些镜像算搜过了，不再报「未建好」，Find 也就不会为它们请求构建。存不了派生数据、又被淘汰了的镜像照旧：作用域内的会被请求重建，搜全部镜像时不会。
4. 启动时 Always Index 的提前读取不再把每个镜像都读进内存：按 Always Index 的顺序读到装满为止。其余镜像在派生数据里，第一次搜索时读回。
5. 打印出的语料照旧当场写进派生数据，写完后和读回的一样受上限约束。

**交叉引用表**
6. 默认驻留上限从 256 MB 改为 64 MB（Settings › Search 的 Cross References 一节）。
7. Keep Cross References Ready 的后台预建改成「装满为止」：先按 Always Index 的顺序、再按其余已索引镜像的顺序，一次预建一个；某个镜像预建完放不进剩下的空间，就不留它、也不为它挤掉已经留着的，后台预建到此为止。为此预建请求多一个选项（只在有空间时留下，不挤掉别人），结果多一个字段（留下了没有）；两者都是可选的线上字段，老的对端照旧按最近使用淘汰。
8. 查询现扫时顺带预建的镜像照旧按最近使用留下，会挤掉最久没用的。

**没有询问就采用的假设**
- 已有设置文件里两个上限若仍是旧默认值 256，视为没改过，升级后改成 64；改过的保留。
- 推出按钮照旧：清掉常驻部分，派生数据里的语料不受影响，搜索时照样读回。
- 读回的语料不另记 Report 行：读回只在搜索里发生，Report 的 Searchable Interfaces 行的大小反映的是常驻部分。
- 没有派生数据的引擎（App 进程内的 Bonjour 引擎、CLI 独立 host、测试）照旧只搜常驻的语料，只是上限变小。

**不做**
- 把语料压缩后留在内存里：省得没有读盘多，搜索还得每次解压。
- 交叉引用表存盘：[0061](0061-derived-data.md) 已决定不存（Release 版预建一个镜像只要零点几秒），本提案不推翻。

**落地步骤**
1. [ ] 语料：上限默认值、优先淘汰能读回的镜像、搜索时按需读回（含测试：上限装不下时搜全部镜像仍搜到每个镜像，峰值只多一个镜像，搜完常驻不超过上限）。
2. [ ] 语料：启动时提前读取到装满为止；搜索摘要不再把能读回的镜像报为未建好（含测试）。
3. [ ] 交叉引用：预建选项与结果字段（线上兼容测试）、协调器按顺序预建到装满为止（含测试：放不下的不留、不挤掉已留的，后续不再预建）。
4. [ ] 设置：两个默认值改为 64 MB，旧默认值迁移；Settings 页与 `Settings+Search.swift` 的说明同步。
5. [ ] 文档与实测：`AGENTS.md`、`Documentations/DerivedData.md`（读取不再只在启动与构建时发生）、术语表；按 2026-11-01 的配置重测两个引擎进程。

## 决策日志

| 日期 | 决定 | 理由 |
|------|------|------|
| 2026-11-01 | Created as Draft | 推出按钮做完后实测，两个引擎进程里语料与交叉引用表仍占约一半；用户选择改成按需常驻，并另查 App 进程那次 699 MB 的峰值（不在本提案）。 |
| 2026-11-01 | 语料只留最近搜过的、默认 64 MB，其余搜索时从派生数据读回 | 用户在「留最近搜过的 64 MB」与「一个都不留、每次搜索都读」之间选了前者：反复搜同一批镜像不读盘，搜全部镜像时多出的读盘在 Release 版约 0.5 秒。 |
| 2026-11-01 | 交叉引用表默认 64 MB，按 Always Index 的顺序预建到装满为止 | 用户在「64 MB 装满为止」「默认关掉预建」「128 MB」之间选了第一个。只调低上限而照旧预建全部镜像的话，后建的会把先建的挤掉，后台白扫一遍，所以要改成装满就停。 |
| 2026-11-01 | 用户批准，开始实现 | 提案随功能分支的第一个提交走：`next` 上有上一篇功能在本地合进来、还没推送的提交，提案不能单独推到 `next`。 |
