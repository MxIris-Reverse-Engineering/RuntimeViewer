摘要

iOS、越狱版 iOS 与 visionOS 的 RuntimeViewer 改成「每个窗口一份文档会话」：Mac 的 Document 里与平台无关的那部分（编号、先启动引擎的后台工作再建界面、关闭时只关自己带来的成员）收成 AppCore 里两端共用的 DocumentSession，iOS 每个 scene 持有一个，iPad 与 visionOS 能开多个窗口。在此之上，iOS 能打开磁盘上的文件：侧栏根页齿轮旁多一个打开按钮，经文档选择器选文件（越狱版另有「Open Path…」按绝对路径打开），也接收「文件」App 里的「用其他 App 打开」；文件在 App 进程里读，能开多窗口的设备上开一个新窗口，iPhone 上叠在当前窗口上面、关掉就回到本机。打开文件、导出日志的格式化、引擎管理器跟随设置这几段平台无关的逻辑进 AppCore，为此 AppCore 在所有平台上链接 RuntimeViewerEngineManagement。边界测试扩到 iOS target。MainViewModel / MainRoute 的合并留到第四步。Mac 的行为不变。

关联

  • 所属愿景：iOS 版功能对齐（第三步「App 层逻辑下沉与 iOS 窗口模型」；MainViewModel / MainRoute 的合并按用户决定挪到第四步）
  • 关联提案：0099（引擎管理在 iOS 上可用、文件在进程里读）、0100、0101、0055、0058、0069、0077
  • 配套文档：待定 —— 预计无单独文档，规则写进 RuntimeViewerUsingUIKit/AGENTS.md

架构图

改了什么

  • 新增
  • 修改
  • 不变

AppCore 多出两端共用的文档会话、窗口注册表、打开文件与两小块逻辑，并在所有平台上链接引擎管理；MainViewModel 那批文件仍只在 macOS，第四步再放开。Mac 的四个控制器改用这些类型，行为不变；iOS 的 scene 从注册表取会话，新的 FileController 负责打开入口。

iOS 上打开一个文件

  • 新增
  • 已有

文件在进程里读，读不了在开窗之前就知道。iPad 与 visionOS 开新窗口，新窗口凭请求号从注册表取走预留的引擎；iPhone 上文件窗口叠在当前窗口上面，关掉即回到本机。最后一个文档离开 30 秒后，引擎从管理器拿掉，安全作用域访问随之结束。

提议方案

  1. AppCore 在所有平台上链接引擎管理：清单里对 RuntimeViewerEngineManagement 的四处依赖都去掉平台条件；HelperClient、CatalystExtensions、Injection 照旧只在 macOS；MainViewModel、MainRoute 及其依赖的那批文件仍是 #if os(macOS)，第四步再放开。
  2. 共用的文档会话 DocumentSession：持有 DocumentState 与进程内从 1 起的编号；open() 在界面绑定之前启动引擎的后台工作，close() 离开并关掉这个文档带来的成员——开过没开过都收尾，关过之后 open() 不再生效；各只生效一次。Mac 的 Document 持有一个，MCP 编号写成 "document\(session.number)"。
  3. iOS 的窗口模型：iOS 与越狱版打开多窗口（visionOS 本来就开着）；AppCore 的 DocumentSessionRegistry 按 UISceneSession.persistentIdentifier 给每个窗口一个会话，进程活着时一直保留，用户关掉窗口时 close()；为文件开的新窗口先预留引擎、拿请求号，scene 连接时取走，取不到（重启后恢复的窗口）就用本机。SceneDelegate 先 open() 再建界面。
  4. 打开文件的共用部分 RuntimeFileOpener：startReading(fileAt:) 在主线程外读文件头，已列出的文件优先，否则配默认依赖缓存，交给管理器；带安全作用域的 URL 一直保持访问，直到引擎被放走。letGoOfFile(readBy:)：file service 里读的挂起，进程里读的从管理器拿掉并结束访问。Mac 的 FileController 改用它。
  5. RuntimeFileEngineParking 放开平台限定，经 letGoOfFile(readBy:) 放走；管理器公开 readsFilesInThisProcess。
  6. 依赖缓存按本机配对：platformNamesPairedWithThisDevice、canPairWithThisDevicesCache(_:) 按平台取值；在进程里读的文件按默认配了本机缓存、本机缓存却打不开时，RuntimeFileOpener 改为单独读。
  7. iOS 的打开入口（iOS target 的 FileController）：齿轮旁的打开按钮（越狱版是 Choose File… 与 Open Path… 的菜单，越狱版在运行时按「没有容器」判断）；「用其他 App 打开」；读成功后多窗口设备开新窗口、iPhone 叠在上面；文件窗口有关闭按钮；读不了就不开窗口，在当前窗口提示原因。
  8. 平台无关的小块逻辑进 AppCore：ApplicationLogs.formattedEntries(since:)、RuntimeEngineManagerSettingsFollower（Mac 读完设置后启动，iOS 在引擎管理器起来之后启动）。
  9. 边界测试扩到 iOS target，iOS 的 MainViewModel 列为唯一例外，第四步删。
  10. 文档：RuntimeViewerUsingUIKit/AGENTS.md 加「窗口与文档会话」「打开文件」两节；RuntimeViewerUsingAppKit/AGENTS.md 与根 AGENTS.md 跟上；愿景表与两份索引登记本篇。

非目标

  • 合并 MainViewModel / MainRoute：第四步做，届时 iOS 照 Mac 走 SelectionRoute。这一步 iOS 的路由不动。
  • iOS 上的切换来源、最近打开、依赖缓存的选择与 Settings › Files 页：第五步。
  • iOS 上导出日志的入口、派生数据：前者用户定了不加，后者照 0100 不开。
  • 派生数据的度量与删除、启动顺序写成共用代码：前者平台无关的部分已在 Core，后者只有两行且调用不同。
  • 把 iOS target 的通用 UIKit 小工具搬进 RuntimeViewerUI：第四步补 AppUI 的 UIKit 一侧时整理。
  • 在单独的进程里读文件、Load Frameworks、附加进程：iOS 上没有。

详细设计

DocumentSession 与 Mac 的调用点 
@MainActor
public final class DocumentSession {
    /// The order this session was made in within this process, from 1.
    public let number: Int
    public let documentState: DocumentState
    public init(runtimeEngine: RuntimeEngine)
    /// Joins the engine's background work. Only the first call does anything.
    public func open()
    /// Leaves it and closes what this document brought into being.
    /// Opened or not; only the first call does anything, and open() does nothing after it.
    public func close()
}

final class Document: NSDocument {
    let session: DocumentSession
    var documentState: DocumentState { session.documentState }
    var mcpIdentifier: String { "document\(session.number)" }
    override func makeWindowControllers() {
        session.open()
        addWindowController(mainCoordinator.windowController)
    }
    override func close() {
        session.close()
        super.close()
    }
}

@MainActor
public final class DocumentSessionRegistry {

    /// requestIdentifier, or on .local when nothing is reserved. Not yet opened.

    /// Closes and forgets the sessions of windows the user closed.

}

iOS 的文件窗口、关闭、越狱版判断与安全作用域
  • 文件窗口：supportsMultipleScenes 为真就 registry.reserveWindow(on:)，把请求号放进类型为 dev.JH.RuntimeViewer.fileWindow 的 NSUserActivity，调 activateSceneSession(for:)（iOS 17 起）；为假就建会话与一套新的 MainCoordinator，open() 之后以 .fullScreen 从当前窗口呈现，FileController 持有它直到关闭。
  • 关闭按钮：文件窗口根页的 xmark（leftBarButtonItem）经 delegate 到 MainCoordinator：叠着的收起并 close()；独立窗口请系统销毁 scene，会话在 didDiscardSceneSessions 里关。
  • 越狱版判断：NSHomeDirectory() 不在 /Containers/Data/Application/ 之下即视为没有容器，菜单里才出现「Open Path…」；不新增编译开关。
  • 安全作用域：按引擎的来源记下已开始访问的 URL，放走引擎后结束访问；读失败当场结束。Mac 的 URL 不带安全作用域，什么也不记。
  • 后台工作在 iOS 上开始跑：交叉引用预建（默认开）、Always Index（默认关）、Find 语料按设置运行，与 Mac 相同；iOS 没有 Report 页，暂由日志观察。

动机

完整动机见愿景《iOS 版功能对齐》。这一步特有的：

  • iOS 的窗口从不启动、也不结束引擎的后台工作：SceneDelegate.swift:15 直接 DocumentState()，Find 语料、交叉引用预建、后台索引在 iOS 上都不会跑，多开一个窗口也没人收尾。Mac 把这两步写死在 Document.swift:40-54，第二个前端只能照抄。
  • iOS 上打不开磁盘上的文件：0099 让管理器能在进程里读文件，但没有入口；打开流程全在 Mac 的 FileController 里，夹着 NSDocumentController 与 NSAlert。
  • iOS 只有一个窗口：iOS 与越狱版的 Info.plist 关着多窗口。
  • 分层在 iOS target 上没人看着：边界测试只扫 macOS target。

前期调研

文档、打开文件与放走文件引擎
  • Mac 的 Document（85 行）：MCP 编号（:6-12）、init(runtimeEngine:)（:20-23）、makeWindowControllers 先 startBackgroundWork()（:40-48）、close() 先 documentWillClose()（:50-54）。编号只有 MCP 读。
  • DocumentState 在 iOS 上本来就编；startBackgroundWork()（:343-346）与 documentWillClose()（:435-440）只能各调一次。
  • Mac 的 FileController：平台无关的是读文件头、选缓存、startReading、waitUntilFileIsRead、parking；AppKit 的是 NSDocumentController、开窗、NSAlert。
  • 在进程里读的文件引擎返回前就读完、读不了就抛错；它「从不挂起」，能把它拿掉的只有 terminateRuntimeEngine(for:because:)。FileReading 是 internal。
  • RuntimeFileEngineParking 整个 #if os(macOS)，对在进程里读的引擎什么也做不了。
  • platformNamesPairedWithThisMac 写死 macOS 与 Mac Catalyst；.systemDyldSharedCache 读 FullDyldCache.cachedHost，打不开就报错。待实测：普通 iOS 的沙盒能否打开本机缓存。
AppCore、路由、日志、设置与 scene
  • AppCore 对引擎管理的依赖只在 macOS（Package.swift:460）；191 个文件里 48 个整个只在 macOS，MainViewModel（627 行）与 MainRoute 在其中。
  • 两份 MainRoute 没有一个 case 相同：Mac 17 个，iOS 4 个；iOS 的 MainViewModel 是 9 行的空壳。
  • 导出日志用 OSLogStore(scope: .currentProcessIdentifier)，iOS 15 起可用。
  • 派生数据平台无关的部分早已在 Core 的 RuntimeDerivedDataMaintenance。
  • 设置生命周期两端读写方式不同，能共用的只有跟随共享缓存开关；iOS 上它的生效值恒为 true，与管理器默认相同。
  • 三份 Info.plist 只有一个 scene 配置；没有文档类型；SceneDelegate 不看 connectionOptions。iPhone 上 supportsMultipleScenes 恒为 false。
  • 边界测试三条检查，扩到 iOS target 今天会报 MainViewModel.swift:7 两次；iOS target 只有 23 个文件。

替代方案考量

8 个方案，均未采用
  • iOS 用 UIDocument：愿景已否。
  • 这一步就合并 MainViewModel / MainRoute：用户定了留到第四步。
  • 共用逻辑放进 RuntimeEngineManager：用户选了让 AppCore 链接引擎管理；读文件头、选缓存要读设置，管理器不依赖设置。
  • iPhone 上把当前窗口换成文件：切换来源要等第五步，换过去回不到本机。
  • 越狱版只用文档选择器：看不到系统路径与别的 App 的二进制。
  • 在进程里读的文件引擎改成可挂起：要等第五步的来源列表才看得见，且要动管理器对引擎身份的假设。
  • scene 断开就关会话：系统会断开后台的 scene，连回来时文件窗口会变成本机。
  • 重启后恢复文件窗口：要存文件书签，Mac 也关掉了窗口恢复。

影响

用户可见变化

  • iOS、越狱版 iOS 与 visionOS：侧栏根页齿轮旁多一个打开按钮；越狱版上是菜单（Choose File…、Open Path…）。
  • 文件在文件窗口里打开：iPad 与 visionOS 上是新窗口，iPhone 上叠在当前窗口上面；关闭按钮关掉它，iPhone 上随即回到本机。读不了的文件不开窗口，提示原因。
  • 「文件」App 的「用其他 App 打开」能选 RuntimeViewer（iOS 与越狱版）。
  • iPad 上能开多个窗口，新窗口看本机。
  • 引擎的后台工作在 iOS 上开始按设置运行（交叉引用预建默认开）。
  • Mac：无变化。

可发现性

打开按钮在齿轮旁；「用其他 App 打开」由系统列出。默认都开，没有开关。

数据与配置兼容

不新增设置键，不改存盘格式。

平台与最低版本

最低版本不变（iOS 18、visionOS 2；activateSceneSession(for:) 要 iOS 17 / visionOS 1）。「Open Path…」只在没有容器的越狱版上出现。

发布

不需要新的 entitlement；iOS 与越狱版的 Info.plist 多了文档类型与就地打开的声明。不影响公证与 Sparkle。
