摘要

C++ 对象树里，同一个作用域中同一个类模板的所有特化收进一个以模板名命名的节点：std::__1 下不再平铺 vector<int, std::__1::allocator<int>>、vector<char, …>……，而是一个 vector 节点，展开后是它的各个特化，特化行照旧显示全名。只有一个特化的模板也收进节点。

节点是新的对象类型 .cPlusPlus(.classTemplate)，绿色 T 图标；选中它，内容区列出全部特化的声明，每行可点击跳到那个特化。归组做在 Core 的对象树里，侧栏、路径栏（jump bar）、镜像页与 iOS 侧栏看到的是同一棵树。模板名取自上游 MachOKitExtensions 现成的 baseName，不解析文本。objectsInImage 请求多一个可选字段，只有声明认识新类型的请求方才拿到分组后的树。命名空间的界面文字与导出结果都不变。

提议方案

  1. 新对象类型：RuntimeObjectKind.CPlusPlus.classTemplate，说明「C++ Class Template」，排在类之后、命名空间之前。它是对象树里的节点，不是镜像里的实体。
  2. 对象树归组：子节点里 baseName 非空且与这一段不同的，按 baseName 分组，每组一个模板节点（name 是父路径加模板名，displayName 是模板名，children 是特化）。一个特化也成组，顶层同样归组。RTTI 现编的中间节点没有 baseName，留在原处；已有同名兄弟时这一组不建节点。
  3. 模板节点的界面：先一行镜像名，再「Specializations of <限定名>」，然后每个特化一行声明，与命名空间的「Declared here」同一写法，可点击跳转。
  4. 命名空间与类的界面文字不变：列内部声明时把模板节点换成它的特化。
  5. 线上兼容：ObjectsInImageCommand 加可选的 includesCPlusPlusClassTemplates，要 C++ 对象时一并设，公开 API 不变；没设时服务端回平铺的特化，与现在逐字节相同。
  6. 导出不变：exportedObjects 只写模板节点的特化。
  7. 界面各处：绿色 T；过滤范围无勾选框；侧栏顶层多一区「C++ Class Template」（只在全局作用域有模板时）；Inspector 无层级页；镜像页多一行计数（同样只在全局作用域有模板时）。

非目标

  • 函数模板不归组；不打印主模板的形参列表（mangling 不记录）。
  • RTTI 现编的中间节点不归组（要上游给 CPlusPlusClass 加每一段的 baseName）。
  • 不把带模板参数的 undetermined 作用域改判成类；不与类混排；不提供开关。
  • Find、MCP、CLI、词云、后台索引从不读 C++ 对象，不受影响。

详细设计

对象类型 
public enum CPlusPlus: Codable, Hashable, Identifiable, CaseIterable, Sendable {
    case `class`
    /// The specializations of one class template in one scope, gathered
    /// under the template's name: a node of the object tree rather than an
    /// entity of the image. Only a requester that says it knows this kind
    /// (`ObjectsInImageCommand.includesCPlusPlusClassTemplates`) is sent one.
    case classTemplate
    case namespace
}

level：类 2、类模板 3、命名空间 4，Objective-C 从 5 起、Swift 从 9 起依次后移。level 私有、从不编码，改编号不影响对端。

对象树与归组规则 
struct CPlusPlusObjectTreeBuilder {
    struct Scope: Sendable {
        var path: [String]
        var baseName: String
        var kind: Kind
        var hasMembers: @Sendable () -> Bool
        var children: [Scope]
    }

    struct ClassName: Sendable {
        var path: [String]
        var baseName: String
    }

    func objects(globalScope: Scope, classes: [ClassName]) -> [RuntimeObject]
}
  1. 每个子节点先做成对象（函数作用域、空命名空间照旧为 nil）。
  2. 子节点是特化，当且仅当对象不为 nil、baseName 非 nil 非空、且 baseName != component。不看 kind：上游不给带模板参数的作用域打类型提示，判不出时 builder 把它做成命名空间。
  3. 按 baseName 分组；某个 baseName 等于任一兄弟的 component 时，这一组不建节点。
  4. 每组一个 RuntimeObject(name: path + baseName, displayName: baseName, kind: .cPlusPlus(.classTemplate), children: specializations.sorted())。
  5. 其余对象加上模板节点，整体 sorted()。
换回平铺的特化与线上字段 
extension RuntimeObject {

struct ObjectsInImageCommand: RuntimeEngineProgressCommand {

模板节点换成它的特化（递归、重新排序），其余对象原样、子树同样处理。_objects 两个重载与 _localObjectsWithProgress 多一个参数，为假时套用它；它只给引擎用。测试再冻结一份「0103 版的请求」。

命名空间与类的声明表、导出改用一层展开的 [RuntimeObject].openingCPlusPlusClassTemplateNodes：模板节点下只有特化，一层就够，C++ 对象按有模板节点之前的顺序重排。导出另有 public var [RuntimeObject].exportedObjects，顶层也按原顺序，单文件格式拼出的 .hpp 与以前逐字相同。

模板节点的界面 
// libc++.1
// Specializations of std::__1::basic_string
class std::__1::basic_string<char, std::__1::char_traits<char>, std::__1::allocator<char>>;
class std::__1::basic_string<wchar_t, std::__1::char_traits<wchar_t>, std::__1::allocator<wchar_t>>;

打印器新增 ClassTemplateDeclaration（qualifiedName、imageName、specializations: [Declared]），复用 declaredSection，所以记号与「Declared here」相同、照旧可点。判不出种类的特化照对象种类印成 namespace X {}。

调研

现状、上游能力与各处消费方
  • 对象树由 CPlusPlusObjectTreeBuilder 逐段建，每段一个节点，displayName 是这一段原文；section 按 name 登记 objectsByName。
  • 上游 CPlusPlusScope.baseName 与 CPlusPlusClass.baseName 由 demangler 语法树给出，文档写明就是让同一类模板的特化共享它；3.0.0 起就有，RV 下限 3.3.0，不用改上游。CPlusPlusClass 只给最后一段。
  • 上游不给带模板参数的作用域打类型提示（CPlusPlusDemangling.cpp:458-478），kind 可能判成 undetermined。
  • RuntimeObjectKind 的 Codable 按 case 名合成，旧解码器遇到新 case 整个回复失败；includesCPlusPlusObjects 是先例，ObjectsInImageCPlusPlusWireTests 用冻结的旧请求守着。
  • RuntimeObject 按 imagePath、kind、displayName 比较；路径栏会对子节点再排一次。
  • 过滤范围按勾选的类型集合过滤，matchesRecursively 让有子孙通过的父节点留下；勾选框来自 allRepresentableKinds。
  • 命名空间与类的界面按 object.children 列出内部声明；导出整棵展开；镜像页只数顶层；Inspector 只给类显示层级与派生类。
  • libc++ 实例化了 basic_string<char> 与 <wchar_t>，可做端到端测试（命名空间是不是 __1 是推测，测试不写死）。

替代方案

8 条，全部否掉
  1. 只在 AppCore 侧栏归组：路径栏、镜像页、iOS 各做一遍，模板节点也没有界面可印。
  2. 用 .cPlusPlus(.class) 加属性位：层级、派生类、Inspector、导出都会当成类；新属性位还得加过滤行；图标分不开。
  3. 自己解析模板参数：上游已有语法树给的 baseName；文本解析会碰上 operator<、嵌套尖括号与 ABI 标签。
  4. 与类按名字混排：要让两种类型比较相等，侧栏顶层两个分区的先后不确定。
  5. 两个以上才归组：用户选了一律归组。
  6. 子项只显示模板参数：用户选了全名。
  7. 不加线上字段：0103 之后的 App 连新版对端时，整个镜像的对象列表解码失败。
  8. 选中模板节点只展开：用户选了列出全部特化。

影响

用户可见变化

  • 侧栏、路径栏与 iOS 侧栏：特化收进绿色 T 的模板节点，行上仍是全名；命名空间里模板节点在类之后、命名空间之前。
  • 选中模板节点，内容区列出全部特化，点击跳转。
  • 全局作用域有模板时，侧栏顶层多一区「C++ Class Template」，镜像页多一行计数。
  • 不变：命名空间与类的界面文字、导出结果、Find、MCP、CLI；过滤范围没有新勾选框。
  • 以前直接点 vector<int, …>，现在先展开 vector；过滤框搜全名照旧直接命中。

可发现性

默认开启、没有开关：这是对象树的显示方式，节点就在列表里。

数据与配置兼容

  • 书签、导航历史、最近对象按 (imagePath, name, kind) 认对象，特化的三项都没变。
  • 记住的过滤范围不受影响。
  • 不同版本的对端三种组合都能读，旧版 App 永远收不到解不开的类型。

平台与最低版本

不变。macOS 与 iOS 家族（共用 AppCore 的侧栏 ViewModel）都显示模板节点。

发布

不需要新权限、entitlement 或隐私清单条目；不影响公证与 Sparkle。
