0095 - 整理 AppCore 与 AppUI 的目录分类

状态 Implemented 创建 2026-11-18 对应提案最后更新：2026-11-18 分支 feature/app-layer-directory-layout（已合进 next）

原文：0095-app-layer-directory-layout.md（以原文为准）。关联提案：0091（拆 AppCore 与 AppUI）、0094（AppCore 不再使用 AppKit/UIKit 模型）。

摘要

把 RuntimeViewerAppCore 与 RuntimeViewerAppUI 的源文件按功能重新归目录，只移动、不改行为。

  • AppCore 根目录下散着的 17 个文件全部收进有名字的目录（App/、Base/、Document/、Extensions/、Filtering/、RuntimeImage/ 等）。
  • 每个 Engine 的后台工作——索引、Find 语料、交叉引用预建、手动加载——从四处收到 BackgroundWork/ 一处。
  • 22 个文件的 Find/ 分出 Query/、Scope/、Results/、CrossReferences/；Sidebar/ 照 App 一侧分成 Root/ 与 RuntimeObject/。
  • AppUI 镜像 AppCore：扩展、绘制或适配某个 AppCore 类型的文件放进与该类型同名的目录，Icons/ 因此拆散。
  • 只拆两个名不副实的文件（Extensions.swift、InspectorViewModel.swift）；测试 target 不动，只改测试里写死的两处路径。
  • 归类规则写进 RuntimeViewerPackages/Sources/AGENTS.md，以后新文件照它放。

要你定的事

批准这份草案后，在 worktree .worktrees/RuntimeViewer-AppLayerDirectoryLayout 里按四步实现，做完在本地合进 next 给你看。澄清提问已定：只拆名不副实的文件；测试 target 不动；先写提案再动手。

动机

  • 根目录成了杂物间。AppCore 根目录 17 个文件、AppUI 6 个，彼此毫无关系：ViewModel 基类、文档状态、存储、过滤、图标、杂项扩展。找一个文件只能靠记名字。
  • 同一类东西分在几处。每个 Engine 的三个后台协调器由 RuntimeEngineBackgroundWork 统一持有，却分散在 BackgroundIndexing/、Find/、Engine/；手动加载在 ManualLoading/；BackgroundWorkProcessActivity 在根目录。
  • Find/ 太大。22 个文件平铺，查询模型、结果树、范围选择、交叉引用、后台协调器混在一起。
  • AppUI 的目录和 AppCore 对不上。RuntimeObjectIcon 在 AppCore 根目录、绘制在 AppUI Icons/；ContentInterface 在 Content/、上色在 Theme/；SelectionRoute 在根目录、修饰键换算在 EditorArea/。
  • 名不副实的文件。Extensions.swift 是三段互不相干的扩展；InspectorViewModel.swift 里没有叫 InspectorViewModel 的类型。

提议方案

  1. 目标根目录不放文件。
  2. 目录按功能分，名字与 App 一侧相同（App、Base、Content、EditorArea、Find、Inspector、Reports、Sidebar/Root、Sidebar/RuntimeObject）；App 没有的按装的东西起名。
  3. Engine 的后台工作归 BackgroundWork/，每种一个子目录；读结果的功能不收它们。
  4. AppUI 镜像 AppCore；只有 AppUI 才有的自成目录或跟着唯一使用者走。
  5. 文件以主类型命名；小辅助类型可留在主类型旁，名不副实的拆开。本次只拆两个。
  6. 规则写进 RuntimeViewerPackages/Sources/AGENTS.md。

非目标

  • 不改代码行为、类型名、访问级别和文件内容。
  • 不把其余约 35 个多类型文件拆成一类型一文件。
  • 不整理测试 target 的目录。
  • 不动别的 target 与 App 一侧的目录。
  • 不合并两份 internal 的 Then.swift（要新增公开模块）。
  • 不更新 FeatureMaps/EditorJumpBar.md（按核对基准 commit 读）和已落地提案等历史记录里的旧路径。

详细设计

写进 RuntimeViewerPackages/Sources/AGENTS.md 的新一节（拟稿）：

## Where a file goes in RuntimeViewerAppCore and RuntimeViewerAppUI

- **Nothing at a target's root.** Every file is in a directory named after a feature: the app's own
  folder name where the app has one (`App`, `Base`, `Content`, `EditorArea`, `Find`, `Inspector`,
  `Reports`, `Sidebar/Root`, `Sidebar/RuntimeObject`), otherwise what the directory holds
  (`BackgroundWork`, `Document`, `Engine`, `Extensions`, `Filtering`, `Presentation`, `RuntimeImage`,
  `RuntimeObject`, `Storage`).
- **An engine's background work is in `BackgroundWork/`**: what `RuntimeEngineBackgroundWork` holds —
  indexing, Find corpora, cross-reference preparation, manual loading — one subdirectory each, with
  its state and results. A feature that reads them (Find, the Report, the toolbar's activity) does not
  hold their files.
- **RuntimeViewerAppUI mirrors RuntimeViewerAppCore.** A file that extends, draws or adapts an AppCore
  type goes in the directory of the same name as that type's. What only AppUI has gets a directory of
  its own (`Theme/`, `RuntimeSourcePicker/`, `Resources/`) or goes with its one user.
- **A file is named after its main type.** Small helper types may stay beside it; a file whose name
  names no type in it, or that holds unrelated things, is split.

两处拆分：新文件只带它要的 import（String+IntegerIndex 只要 Foundation；RuntimeImageNode+Sequence 要 RuntimeViewerCore；RuntimeImageLoadState+CaseAccessible 另要 RuntimeViewerArchitectures）。拆出来的代码一字不改。

git 历史：一律 git mv，每步一个提交、提交里只有移动加测试路径或文档，git log --follow 与 blame 都能跟过去。

前期调研
  • 现状（next 上 20d56e71）：AppCore 131 个文件，根目录 17、Find/ 22、Sidebar/ 15；AppUI 39 个，根目录 6。
  • App 一侧目录：App、Base、BatchExporting、Content、EditorArea、Find、Inspector、Main、Reports、Sidebar（下分 Root/、RuntimeObject/，私有声明与 Filter Scope 的视图都在 RuntimeObject/）。
  • 使用者统计：SelectionRoute 被五个目录使用；NavigatorTextFilter 被 Sidebar、Find、Reports 使用，FilterEngine 只被 Sidebar 使用；OwnerReportingTask 只被 App 的批量导出使用；NSColor+Xcode 的颜色只被 FindResultCellStyle 与 App 的 FindViewController 使用。
  • 依赖路径的地方：Package.swift 只声明 Resources/Symbols.xcassets；Tuist 描述只列 target；测试里只有 AppCoreBoundaryTests 写死了五处路径；源码没有 #filePath。
  • 现行文档：根 AGENTS.md 第 809 行，RuntimeViewerPackages/Sources/AGENTS.md 第 22、74–120 行。
替代方案考量
  • 一个文件一个顶层类型：多出约 60 个文件，很多辅助类型只有几行。用户选了只拆名不副实的。
  • 按层分目录（ViewModels / Models / Services）：同一功能分散三处，与 App 一侧按功能分对不上。
  • AppUI 按「做什么」分（保留 Icons/、Theme/）：从 AppCore 类型找绘制代码没有规律。
  • 语料与交叉引用协调器留在 Find/：它们是 Engine 范围的工作，放在 Find/ 会让人以为随 Find 面板创建。
  • 测试 target 一起整理：用户选了先不动。
